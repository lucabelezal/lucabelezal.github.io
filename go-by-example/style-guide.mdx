Este é o meu style guide de Go: o melhor de cada guia, sintetizado em um documento só. Em vez de seguir um texto de ponta a ponta, escolho regra a regra aquela que maximiza dois resultados ao mesmo tempo — **manutenção**, para o código sobreviver a mudanças sem quebrar, e **legibilidade**, para o próximo leitor entender sem pedir ajuda.

As fontes são os três documentos que li por completo: o [Effective Go](https://go.dev/doc/effective_go), o [Go Style Guide do Google](https://google.github.io/styleguide/go/) e o [Go Style Guide do Uber](https://github.com/uber-go/guide) ([tradução pt-BR](https://github.com/alcir-junior-caju/uber-go-style-guide-pt-br)). Quando os guias discordam, escolho o lado com maior ganho de manutenção e legibilidade, e registro o motivo em vez de fingir consenso.

## Parte 1 — Princípios

### 1.1 Ordene os princípios

:::note[Regra]

Quando duas regras entram em conflito, decido nesta ordem: clareza, simplicidade, concisão, manutenibilidade e, por último, consistência.

:::

O [Google guide](https://google.github.io/styleguide/go/guide#style-principles) deixa essa ordem explícita e diz que consistência nunca vence clareza. Faz sentido: um pacote inteiro com nomes ruins continua ruim, mesmo que seja consistente do começo ao fim. Código é lido muito mais vezes do que escrito, então o leitor importa mais que o autor.

### 1.2 Consistência local só onde o guia silencia

:::note[Regra]

Se o código vizinho do mesmo pacote já tomou uma posição e nenhuma regra objetiva deste guia se aplica, eu sigo o vizinho.

:::

Consistência local reduz atrito de review, mas [só vale onde o guia não decidiu](https://google.github.io/styleguide/go/guide#local-consistency). Duas coisas nunca podem virar exceção local: limite de linha e biblioteca de asserção em teste. São decisões que o guia já tomou.

### 1.3 Menos mecanismo possível

:::note[Regra]

Uso um construto da linguagem antes da stdlib, a stdlib antes de uma dependência externa, e uma dependência externa só quando ela resolve um problema real. Nunca trago um framework "por precaução".

:::

O Google chama isso de [least mechanism](https://google.github.io/styleguide/go/guide#least-mechanism). Cada dependência é superfície de manutenção, de segurança e de compatibilidade. Um `map[string]bool` resolve set; não preciso importar uma biblioteca de set para isso.

:::tip[Regra prática]

Antes de adicionar mecanismo, pergunte se a própria linguagem já resolve o problema.

:::

## Parte 2 — Formatação e estrutura de arquivo

### 2.1 `gofmt` decide

:::note[Regra]

Formatação é responsabilidade do `gofmt`, sem discussão. O editor roda `gofmt` (ou `goimports`) ao salvar.

:::

O [Effective Go](https://go.dev/doc/effective_go#formatting) delegou isso à máquina em 2009, e quem lê Go já espera o formato canônico. Discussão de formatação é a menos consequente de todas e a que mais gasta energia em review.

### 2.2 Código gerado também é formatado

:::note[Regra]

Código gerado passa por `gofmt` igual ao código escrito à mão.

:::

O [Google](https://google.github.io/styleguide/go/guide#formatting) formata código gerado via `format.Source`, porque ele também é lido e navegado. Com o arquivo formatado, o diff e o review ficam limpos.

### 2.3 Sem limite rígido de linha

:::note[Regra]

Não uso teto de colunas. Quebro a linha quando a leitura piora, nunca antes de uma mudança de indentação, e não fatio string literal longa.

:::

O Google [não fixa limite](https://google.github.io/styleguide/go/guide#line-length) e avisa que quebrar antes de mudar a indentação confunde o leitor. O Uber sugere [99 colunas como alvo suave](https://github.com/uber-go/guide#avoid-overly-long-lines). Se a linha passa de ~100 e incomoda, refatoro — extraindo a expressão em uma variável local — em vez de fatiar.

```go title="linha-longa.go"
// Errado: condição longa quebrada em duas linhas — o leitor perde o `if`.
if user.Status == StatusActive && user.LastSeen.After(threshold) &&
	user.IsAdmin {
	grant(user)
}

// Certo: extrai a intenção em um nome; a condição volta a uma linha.
canBypass := user.Status == StatusActive && user.IsAdmin
if canBypass {
	grant(user)
}
```

### 2.4 Agrupe declarações relacionadas

:::note[Regra]

`import`, `const`, `var` e `type` relacionados ficam em um único bloco. Não agrupo declarações que não têm relação entre si.

:::

O [Uber](https://github.com/uber-go/guide#group-similar-declarations) mostra que o bloco comunica coesão e reduz ruído visual. Dentro de uma função, variáveis adjacentes podem ser agrupadas mesmo sem relação direta.

```go title="agrupar.go"
// Errado: uma declaração por linha sem necessidade.
const maxRetries = 3
const defaultTimeout = 5 * time.Second

// Certo: mesmo domínio, mesmo bloco.
const (
	maxRetries     = 3
	defaultTimeout = 5 * time.Second
)
```

### 2.5 Dois grupos de import — três quando há proto

:::note[Regra]

O primeiro grupo é a stdlib, o segundo é todo o resto, e o terceiro (só quando existir) são os protos. Import de side-effect (`import _`) vai no fim, em grupo próprio.

:::

O Uber usa [dois grupos](https://github.com/uber-go/guide#import-group-ordering), que é o padrão do goimports. O Google usa [quatro](https://google.github.io/styleguide/go/decisions#import-grouping): stdlib, outros, proto e side-effect. Como meus projetos ainda não usam proto, adoto dois e separo o terceiro quando os protos entrarem. A regra que carrego é uma só: ordem estável e visível de relance.

### 2.6 Ordene funções por receptor e fluxo de chamada

:::note[Regra]

Em um arquivo, `type`/`const`/`var` vêm primeiro, `New*` logo após o tipo, métodos exportados antes dos unexportados, e funções utilitárias sem receptor no fim.

:::

O [Uber](https://github.com/uber-go/guide#function-grouping-and-ordering) recomenda essa ordem porque o leitor percorre o arquivo na mesma sequência em que o código é chamado. Isso reduz a ida e volta para entender um fluxo.

### 2.7 Assinaturas e controle em uma linha

:::note[Regra]

Assinatura de função fica em uma linha, e `if`, `for` e `switch` também. Se não cabe, extraio a expressão em uma variável local em vez de quebrar a cláusula.

:::

O Google exige [assinatura em linha única](https://google.github.io/styleguide/go/decisions#function-formatting) e proíbe quebrar a cláusula de [estruturas de controle](https://google.github.io/styleguide/go/decisions#conditional-formatting). Quando você quebra, a continuação alinha com o bloco indentado e o leitor perde onde o corpo começa.

:::tip[Regra prática]

A máquina formata o código; o humano decide nome, tamanho e ordem.

:::

## Parte 3 — Nomes

### 3.1 MixedCaps; sem underscore em identificador

:::note[Regra]

Uso `camelCase` e `PascalCase`. Nunca `snake_case` em variável, função, tipo, constante ou pacote.

:::

É a convenção da linguagem ([Effective Go](https://go.dev/doc/effective_go#mixed-caps)), e o Google [bane underscores](https://google.github.io/styleguide/go/decisions#underscores) com poucas exceções. Funções de teste podem usar `_` para agrupar casos, como `TestFormat_ComErro`, o que o [Uber](https://github.com/uber-go/guide#function-names) também aceita.

### 3.2 Constantes em MixedCaps, nomeadas pelo papel

:::note[Regra]

Escrevo `const MaxPacketSize = 1500`. Nunca `MAX_PACKET_SIZE`, nem prefixo `k`. O nome descreve o papel, não o valor.

:::

O [Google decisions](https://google.github.io/styleguide/go/decisions#constant-names) observa que uma constante de valor puro, como `const Twelve = 12`, não comunica nada. Quem lê `MaxPacketSize` entende a intenção sem olhar o número.

### 3.3 Iniciais seguem a prosa

:::note[Regra]

Escrevo `URL`, `ID` e `API` com maiúsculas, como na prosa, e não `Url` ou `Id`. Quando o nome não é exportado, começo em minúscula (`url`, `id`).

:::

Segundo o [Google decisions](https://google.github.io/styleguide/go/decisions#initialisms), `Url` e `Id` parecem errados para quem lê inglês. Já grafias consagradas como `iOS` e `gRPC` seguem a forma original.

### 3.4 Pacote com nome curto, que descreve o que oferece

:::note[Regra]

O pacote usa uma palavra minúscula, com o nome igual à base do diretório. Curto, porque é digitado em toda chamada; sem `util`, `common`, `helpers` ou `lib`; e não no plural.

:::

Vale o que dizem o [Effective Go](https://go.dev/doc/effective_go#package-names) e o [Uber](https://github.com/uber-go/guide#package-names). `bytes.Buffer` lê melhor que `bufferutil.Buffer`, e a stdlib usa `net/url`, não `net/urls`.

### 3.5 Getter sem `Get`

:::note[Regra]

Método de leitura usa o nome do campo: `Owner()`, não `GetOwner()`. Palavras como `Fetch` e `Compute` sinalizam uma operação cara.

:::

[Effective Go](https://go.dev/doc/effective_go#Getters) e [Google](https://google.github.io/styleguide/go/decisions#getters) concordam que `Get` não adiciona informação. `Owner()` já diz o que retorna. Nome de função que retorna valor é substantivo (`JobName`); que executa ação é verbo.

### 3.6 Interface de um método termina em `-er`

:::note[Regra]

Uso `Reader`, `Writer`, `Formatter`. Métodos canônicos como `Read`, `Write` e `String` mantêm nome e assinatura canônicos.

:::

O [Effective Go](https://go.dev/doc/effective_go#interface-names) explica que honrar os nomes estabelecidos torna a interface reconhecível. Por isso o método é `String()`, e não `ToString()`.

### 3.7 Nome reflete uso, não origem nem tipo

:::note[Regra]

A variável se chama pelo que representa no contexto: `users`, não `userSlice`; `id`, não `in.GetUserID()`. O nome cresce junto com o escopo.

:::

O [Google](https://google.github.io/styleguide/go/best-practices#variable-names) sistematiza o que o Effective Go sugere: o nome vem do problema, não do tipo. Repetir o tipo ou a origem vira ruído.

```go title="variavel.go"
// Errado: o nome repete o tipo e a origem.
for _, userPointer := range users {
	processUser(userPointer)
}

// Certo: o nome diz o papel.
for _, u := range users {
	process(u)
}
```

### 3.8 Receiver curto e consistente

:::note[Regra]

O receiver tem uma ou duas letras, é uma abreviação do tipo e se repete igual em todos os métodos daquele tipo. Nunca uso `this` nem `self`.

:::

Segundo o [Google decisions](https://google.github.io/styleguide/go/decisions#receiver-names), o receiver se repete em toda assinatura do tipo, então um nome longo multiplica o ruído.

### 3.9 Nome de função não repete a assinatura

:::note[Regra]

Omito do nome o que a assinatura já diz. Escrevo `yamlconfig.Parse`, não `ParseYAMLConfig`, e `Marshal`, não `MarshalToString`. Quando duas funções diferem só no tipo, o tipo diferencia: `ParseInt` e `ParseInt64`.

:::

O [Google best-practices](https://google.github.io/styleguide/go/best-practices#function-names) resume a ideia: o nome soma informação à assinatura, não repete o que já está ali.

### 3.10 Não faça shadowing de nomes da stdlib

:::note[Regra]

É proibido criar uma variável chamada `url`, `http` ou `json` que esconda o pacote. Prefiro renomear a variável (`endpoint`) ou usar o sufixo `pkg` no import (`urlpkg`) quando for inevitável.

:::

Como alerta o [Google best-practices](https://google.github.io/styleguide/go/best-practices#shadowing), o shadowing compila em silêncio e quebra usos posteriores do pacote sem erro nenhum.

### 3.11 Não reuse nome de built-in

:::note[Regra]

É proibido nomear variável ou campo `error`, `string`, `len` ou `new`. Prefiro `err`, `str` e `n`.

:::

O [Uber](https://github.com/uber-go/guide#avoid-using-built-in-names) mostra que reusar um identificador pré-declarado cria shadowing difícil de grep: `error` e `f.error` ficam visualmente parecidos. O `go vet` aponta, mas é melhor nem escrever.

:::tip[Regra prática]

O nome diz o papel; quem lê não precisa saber o tipo nem o pacote.

:::

## Parte 4 — Comentários e documentação

### 4.1 Doc comment explica o porquê, não o quê

:::note[Regra]

Comentário em declaração exportada explica **por que** aquele comportamento existe e quais casos não são óbvios. Não descreve o que o código já deixa claro, e não existe comentário redundante.

:::

Valem o [Effective Go](https://go.dev/doc/effective_go#commentary) e o princípio de clareza do [Google guide](https://google.github.io/styleguide/go/guide#clarity). Comentário que repete o código é manutenção a mais; quando o código muda e o comentário fica, ele vira mentira.

### 4.2 Doc comment abre com o nome, frase completa

:::note[Regra]

Escrevo `// A Request representa uma requisição HTTP.` — começando pelo nome do símbolo e formando uma frase completa, com ponto final.

:::

O [Google](https://google.github.io/styleguide/go/decisions#doc-comments) exige essa disciplina porque godoc e as ferramentas de busca dependem do padrão. Comentário de campo no fim da linha pode ser um fragmento.

### 4.3 Exemplos executáveis nos testes

:::note[Regra]

Exemplo que demonstra uma API vai em arquivo `_test.go`, como `ExampleXxx`: ele roda e aparece no godoc. Trecho que não roda pode ficar em comentário.

:::

Segundo o [Google decisions](https://google.github.io/styleguide/go/decisions#examples), exemplo que executa nunca mente.

### 4.4 Comente o pacote uma vez, acima do `package`

:::note[Regra]

Há um único comentário de pacote, imediatamente acima do `package`, sem linha em branco no meio. Quando é longo, ele fica em um `doc.go` com o comentário e a cláusula `package`.

:::

O [Google decisions](https://google.github.io/styleguide/go/decisions#package-comments) lembra que esse comentário é a porta de entrada do pacote no godoc. Em `package main`, o nome do binário abre a frase.

### 4.5 Comentário em frase completa; sem teto de linha

:::note[Regra]

Doc comment é frase completa, capitalizada e pontuada. Comentário de fim de linha pode ser fragmento. Não existe coluna fixa: 80 ou 100 são comuns, desde que o arquivo seja consistente.

:::

O [Google decisions](https://google.github.io/styleguide/go/decisions#comment-sentences) prefere a sentença completa porque ela lê como documentação. Já uma frase jogada em uma linha larguíssima obriga rolagem horizontal.

### 4.6 Documente só o não óbvio

:::note[Regra]

Em parâmetros, campos e options, documento o que é propenso a erro ou surpreendente, e não enumero o óbvio. Cancelamento de context é implícito; só documento quando o comportamento diverge.

:::

O [Google](https://google.github.io/styleguide/go/best-practices#documentation-conventions-params) usa `format is the format` como anti-exemplo: um bom comentário diz o que o leitor não deduz sozinho.

:::tip[Regra prática]

O comentário explica o porquê; o quê o código já mostra.

:::

## Parte 5 — Variáveis e declarações

### 5.1 `:=` para valor explícito; `var` para zero value

:::note[Regra]

Uso `s := "foo"` quando atribuo um valor. Uso `var filtered []int` quando o ponto é o zero value, como slice vazio, struct zero ou alvo de unmarshal.

:::

O [Uber](https://github.com/uber-go/guide#local-variable-declarations) explica a diferença de leitura: `:=` comunica "valor definido", enquanto `var` comunica "começa vazio e pronto para uso". `var user User` é mais claro que `user := User{}`.

```go title="declarar.go"
// Errado: aloca e depois append.
filtered := []int{}

// Certo: nil slice já é utilizável por append/range.
var filtered []int
```

### 5.2 `nil` é slice válido

:::note[Regra]

Retorno vazio é `nil` ou `var s []T`, nunca `[]T{}`. Testo vazio com `len(s) == 0`, nunca com `s == nil`.

:::

O [Uber](https://github.com/uber-go/guide#nil-is-a-valid-slice) e o [Google](https://google.github.io/styleguide/go/decisions#nil-slices) concordam. Dois lembretes: a serialização pode distinguir `nil` de `[]`, e eu não desenho uma API em que o chamador precise distinguir os dois — quem precisa sabe que isso é cheiro de design.

### 5.3 Globals unexported: cuidado com shadowing acidental

:::note[Regra]

Global não exportado tem nome descritivo, como `defaultPort`. Não adoto o prefixo `_` do Uber.

:::

O Uber pede [`_defaultPort`](https://github.com/uber-go/guide#prefix-unexported-globals-with-_) para sinalizar o escopo de pacote, mas a comunidade e o golint usam `defaultPort`. Minha régua: globals são raros (ver 5.4), e quando existem o risco de shadowing some com nomes longos. Erro sentinela unexported segue `errNotFound` nos dois guias, como exceção explícita à regra do `_`.

### 5.4 Sem estado global mutável

:::note[Regra]

Biblioteca não tem variável de pacote que muda em runtime, nem registro de callbacks, nem singleton preguiçoso. Configuração entra por construtor.

:::

O [Google best-practices](https://google.github.io/styleguide/go/best-practices#global-state) mostra que estado global quebra o isolamento de teste: um teste muda o estado e corrompe o seguinte. O [Uber](https://github.com/uber-go/guide#avoid-mutable-globals) mostra a alternativa com injeção.

```go title="global.go"
// Errado: global mutável que todo teste compartilha.
var httpClient = &http.Client{Timeout: 10 * time.Second}

// Certo: dependência do construtor.
func New(opts ...Option) *Client {
	c := &Client{http: &http.Client{Timeout: 10 * time.Second}}
	for _, o := range opts {
		o.apply(c)
	}
	return c
}
```

### 5.5 Reduza o escopo de variáveis

:::note[Regra]

A variável vive no menor escopo que o uso permite, como em `if err := f(); err != nil`. Se o valor é preciso fora do `if`, o escopo maior é o certo; não sacrifico isso para "reduzir escopo".

:::

O [Uber](https://github.com/uber-go/guide#reduce-scope-of-variables) lembra que escopo menor é menos estado para o leitor carregar. Quando entra em conflito, reduzir aninhamento (7.2) tem prioridade.

:::tip[Regra prática]

`:=` diz "tem valor"; `var` diz "começa vazio e utilizável".

:::

## Parte 6 — Erros

### 6.1 Erro é valor; nunca compare string

:::note[Regra]

Uso `errors.Is` e `errors.As`, com sentinela ou `var Err...`, quando o chamador precisa casar o erro. É proibido comparar o texto da mensagem.

:::

O [Google](https://google.github.io/styleguide/go/decisions#errors) e o [Uber](https://github.com/uber-go/guide#errors) concordam: a mensagem muda sem mudar o significado, e a comparação por string quebra em silêncio. Quando o chamador precisa de detalhe estruturado, como arquivo ou operação, o erro carrega campos (`os.PathError.Op/Path`), não texto.

### 6.2 Escolha do tipo de erro

:::note[Regra]

Sigo a matriz do [Uber](https://github.com/uber-go/guide#error-types):

| Precisa casar? | Mensagem | Ferramenta |
| --- | --- | --- |
| Não | estática | `errors.New` |
| Não | dinâmica | `fmt.Errorf` |
| Sim | estática | `var ErrFoo = errors.New(...)` |
| Sim | dinâmica | tipo customizado + `errors.As` |

:::

Sentinela e tipo exportado viram API pública, então eu só exporto quando o contrato exige matching.

### 6.3 Wrap com `%w` no fim; sentinela no começo

:::note[Regra]

O contexto novo vem antes do erro original: `fmt.Errorf("abrir config: %w", err)`. A exceção é a sentinela, que lidera: `fmt.Errorf("%w: cabeçalho inválido", ErrParse)`. Uso `%v` só quando quero ocultar a causa de propósito.

:::

O [Google best-practices](https://google.github.io/styleguide/go/best-practices#error-percent-w) explica que o `%w` no fim faz a cadeia impressa ir do erro mais novo ao mais antigo, e que a sentinela no começo garante que a categoria apareça primeiro. O [Uber](https://github.com/uber-go/guide#error-wrapping) resume: se o chamador deve casar, `%w`; senão, `%v`.

### 6.4 Sem "failed to" empilhado

:::note[Regra]

Escrevo o contexto como substantivo: `"new store: %w"`, e não `"failed to create new store: %w"`.

:::

O [Uber](https://github.com/uber-go/guide#error-wrapping) mostra que `failed to x: failed to y` empilha e ninguém sabe onde começa o problema real. A cadeia `x: y: new store: the error` lê como causa.

```go title="wrap.go"
s, err := store.New()
if err != nil {
	// Errado: "failed to create new store: ..."
	// Certo:    "new store: ..."
	return fmt.Errorf("new store: %w", err)
}
```

### 6.5 Mensagens minúsculas, sem pontuação final

:::note[Regra]

Escrevo `errors.New("usuario nao encontrado")`, sem maiúscula inicial (exceto nome próprio ou acrônimo) e sem ponto final.

:::

O [Google decisions](https://google.github.io/styleguide/go/decisions#error-strings) lembra que a mensagem vira prefixo quando outro `%w` a envolve, então maiúscula e ponto viram ruído no meio da cadeia. Para exibição final, em log ou UI, capitalizo no ponto de exibição.

### 6.6 Loga OU retorna; nunca os dois

:::note[Regra]

Cada erro é tratado uma vez. Quem loga decide a mensagem; quem retorna decide a cadeia. Logar **e** retornar o mesmo erro duplica ruído em toda a pilha.

:::

Vale o [Uber](https://github.com/uber-go/guide#handle-errors-once) e o [Google](https://google.github.io/styleguide/go/best-practices#error-logging). Existem três saídas legítimas: envolver e retornar, logar e degradar, ou casar a sentinela e degradar com `errors.Is`, envolvendo o resto.

### 6.7 Sem erro in-band

:::note[Regra]

Função que pode falhar retorna `(valor, err)` ou `(valor, ok)`. Nunca uso `-1` ou `""` mágico como erro.

:::

O [Google decisions](https://google.github.io/styleguide/go/decisions#in-band-errors) mostra que o erro dentro do valor esconde a falha e convida a esquecer o tratamento. O retorno explícito força a decisão.

```go title="in-band.go"
// Errado: -1 como "não achou" mistura dado e erro.
func IndexOf(list []int, want int) int

// Certo: ok separa o resultado do sucesso.
func Find(list []int, want int) (index int, ok bool)
```

### 6.8 Type assertion sempre com comma-ok

:::note[Regra]

Escrevo `t, ok := i.(string)`. A forma de um retorno só quando o panic é o comportamento desejado, e isso nunca acontece em produção.

:::

Segundo o [Uber](https://github.com/uber-go/guide#handle-type-assertion-failures), `t := i.(string)` panica quando o tipo é errado.

### 6.9 Asserção com `t.Fatal` em teste, não `panic`

:::note[Regra]

Em teste, falha de setup usa `t.Fatal` ou `t.FailNow`, nunca `panic`.

:::

O [Uber](https://github.com/uber-go/guide#dont-panic) observa que `panic` em teste marca a falha de forma imprecisa e pode mascarar o caso que estava rodando.

### 6.10 Nomeie erros: `ErrFoo`, `errFoo`, `FooError`

:::note[Regra]

Sentinela exportada é `ErrFoo`; unexported é `errFoo`, e não `_errFoo`; tipo de erro tem sufixo `Error`, como `NotFoundError`.

:::

O [Uber](https://github.com/uber-go/guide#error-naming) e o [Google GoTip #106](https://google.github.io/styleguide/go/index#gotip) usam o prefixo `Err`/`err` para valor sentinela e o sufixo `Error` para tipo. É uma exceção explícita à regra do `_` em globals unexported.

### 6.11 `errors.Join` e múltiplos `%w`

:::note[Regra]

Para agregar falhas independentes, uso `errors.Join(err1, err2)`. Desde o Go 1.20, `fmt.Errorf` também aceita mais de um `%w`.

:::

Assim a cadeia de cada erro continua inspecionável por `errors.Is` e `errors.As`, sem eu ter que escolher uma única causa.

### 6.12 `%w` vira contrato público

:::note[Regra]

Uso `%w` quando o chamador deve inspecionar a causa, e documento e testo isso. Uso `%v` quando quero apenas anotar ou traduzir para outro espaço de erro, como RPC ou storage.

:::

O [Google best-practices](https://google.github.io/styleguide/go/best-practices#error-extra-info) alerta que quem faz `errors.Is` passa a depender do erro interno. Isso vira parte da API e precisa ser garantido.

:::tip[Regra prática]

O erro sobe como valor; a categoria lidera a mensagem e a causa fecha.

:::

## Parte 7 — Estruturas de controle

### 7.1 Trate o erro primeiro, mantenha o caminho feliz sem indentação

:::note[Regra]

A condição de erro ou saída vem primeiro, com `return` ou `continue`, e o fluxo feliz desce a página sem `else`. O `else` só sobrevive quando as duas pernas atribuem a mesma variável.

:::

O [Google decisions](https://google.github.io/styleguide/go/decisions#indent-error-flow) e o [Uber](https://github.com/uber-go/guide#reduce-nesting) concordam que aninhamento profundo esconde o fluxo principal.

```go title="flow.go"
// Errado: happy path indentado, erro tratado por último.
for _, v := range data {
	if v.F1 != 1 {
		log.Printf("v inválido: %v", v)
		continue
	}
	if err := process(v); err == nil {
		send(v)
	} else {
		return err
	}
}

// Certo: erros primeiro, fluxo desce reto.
for _, v := range data {
	if v.F1 != 1 {
		log.Printf("v inválido: %v", v)
		continue
	}
	if err := process(v); err != nil {
		return err
	}
	send(v)
}
```

### 7.2 Reduza aninhamento

:::note[Regra]

Prefiro `if v.F1 != 1 { continue }` antes do corpo a um `if v.F1 == 1 { ... } else { ... }` aninhado.

:::

O [Uber](https://github.com/uber-go/guide#reduce-nesting) lembra que cada nível de indentação é estado mental extra para o leitor.

### 7.3 Sem Yoda

:::note[Regra]

A variável fica sempre do lado esquerdo da comparação: `if len(s) == 0`, nunca `if 0 == len(s)`.

:::

O [Google decisions](https://google.github.io/styleguide/go/decisions#conditionals-and-loops) observa que, em Go, o compilador já pega atribuição acidental; a forma Yoda só prejudica a leitura.

### 7.4 `break` em switch não sai do loop

:::note[Regra]

Para sair de um `for` de dentro de um `switch`, uso `break loop` com label. `break` sozinho dentro de um `case` é redundante, e eu não escrevo.

:::

Segundo o [Google decisions](https://google.github.io/styleguide/go/decisions#switch-and-break), `break` dentro do switch quebra o switch, não o loop; o label torna a intenção explícita. Um comentário substitui o `break` final desnecessário.

:::tip[Regra prática]

Trate a exceção cedo e deixe o caminho feliz descer reto.

:::

## Parte 8 — Dados: slices, maps, structs

### 8.1 Copie na fronteira

:::note[Regra]

Ao receber ou devolver slice ou map, copio, salvo contrato explícito de não retenção. Não guardo referência ao slice ou map do chamador, e não devolvo estado interno protegido por mutex.

:::

O [Uber](https://github.com/uber-go/guide#copy-slices-and-maps-at-boundaries) explica que slice e map compartilham o array ou mapa subjacente, então a mutação do outro lado vira data race ou estado corrompido.

```go title="copy.go"
func (d *Driver) SetTrips(trips []Trip) {
	d.trips = make([]Trip, len(trips))
	copy(d.trips, trips)
}

func (s *Stats) Snapshot() map[string]int {
	s.mu.Lock()
	defer s.mu.Unlock()

	out := make(map[string]int, len(s.counters))
	for k, v := range s.counters {
		out[k] = v
	}
	return out // nunca devolve s.counters direto
}
```

### 8.2 Struct init com nome de campo

:::note[Regra]

Uso `User{FirstName: "ana", LastName: "silva"}`, sempre com nome, salvo tabela de teste com até três campos.

:::

O [Uber](https://github.com/uber-go/guide#initializing-structs) e o [Google](https://google.github.io/styleguide/go/decisions#literal-field-names) mostram que o literal posicional de um tipo externo quebra se o pacote reordenar os campos, e o `go vet` já reclama. Omito campo zero quando ele não agrega contexto; se o zero é justamente o ponto do teste, nomeio.

### 8.3 Struct referência: `&T{}`, não `new(T)`

:::note[Regra]

Escrevo `sptr := &T{Name: "bar"}`. Reservo `new(T)` para o caso em que só o zero value faz sentido.

:::

O [Uber](https://github.com/uber-go/guide#initializing-struct-references) prefere `&T{...}` por consistência com os literais de valor. `new(T)` e `&T{}` são equivalentes; a partir do Go 1.26, `new(value)` também inicializa um valor.

### 8.4 Map: literal para conjunto fixo; `make` para vazio/programático

:::note[Regra]

Elementos fixos conhecidos vão em literal. Map vazio ou preenchido em loop usa `make(map[...]..., hint)`.

:::

O [Uber](https://github.com/uber-go/guide#initializing-maps) lembra que `make` distingue declaração de inicialização e aceita hint. Ponto importante: ler de um map `nil` é ok, mas **escrever** nele panica, então inicializo antes de mutar.

### 8.5 Capacity hint quando o tamanho é conhecido

:::note[Regra]

Uso `make([]T, 0, n)` e `make(map[K]V, n)` quando sei ou estimo o tamanho antes do append.

:::

A [performance do Uber](https://github.com/uber-go/guide#prefer-specifying-container-capacity) mostra que a capacity de slice é exata, com zero alloc até o limite. O hint de map é uma aproximação de buckets. E isso **só no hot path**: regra de performance não vira micro-otimização em todo lugar.

### 8.6 Mutex: campo, nunca embedded

:::note[Regra]

Uso `mu sync.Mutex` como campo nomeado. Embedding de `sync.Mutex` é proibido até em struct unexported.

:::

O [Uber](https://github.com/uber-go/guide#zero-value-mutexes-are-valid) e o [Google](https://google.github.io/styleguide/go/decisions#copying) explicam que o embedding promove `Lock` e `Unlock` à API pública do struct e esconde que o tipo não pode ser copiado. `var mu sync.Mutex`, o zero value, é o correto; `new(sync.Mutex)` é desnecessário.

```go title="mutex.go"
// Certo.
type Counter struct {
	mu sync.Mutex
	n  int
}

// Errado: Lock/Unlock viram métodos públicos de Counter.
type Counter struct {
	sync.Mutex
	n int
}
```

### 8.7 Embedding: só com benefício tangível

:::note[Regra]

Embedding existe quando todos os métodos internos **deveriam** virar métodos do tipo externo. O teste é: "eu adicionaria cada método exportado do interno direto no externo?". Se a resposta é "alguns" ou "não", uso campo nomeado. Embedded fica sempre no topo da lista de campos.

:::

Valem o [Uber](https://github.com/uber-go/guide#embedding-in-structs) e o Effective Go. Embedding de `io.ReadWriter`, uma interface, quebra o zero value útil (`var b Book` dá nil panic); embedding de `bytes.Buffer` preserva. Embedding em struct exportado também vaza implementação e trava a evolução do tipo.

### 8.8 Field tags em struct serializada

:::note[Regra]

Todo campo que vira JSON, YAML ou outro formato tag-based recebe tag explícita, mesmo quando o nome coincide.

:::

Segundo o [Uber](https://github.com/uber-go/guide#use-field-tags-in-marshaled-structs), a forma serializada é um contrato entre sistemas; a tag torna o contrato explícito e protege contra rename acidental.

```go title="tags.go"
type Stock struct {
	Price int    `json:"price"`
	Name  string `json:"name"`
}
```

:::tip[Regra prática]

Slice e map são referências: compartilhou, compartilhou mutação.

:::

## Parte 9 — Structs, tipos e zero value

### 9.1 Projete o zero value para ser útil

:::note[Regra]

Um tipo novo começa utilizável com o zero value quando isso faz sentido — `bytes.Buffer` e `sync.Mutex` documentam "zero value ready". Documento quando o zero value é utilizável e quando não é.

:::

O [Effective Go](https://go.dev/doc/effective_go#allocation_new) mostra o ganho: quem usa o tipo não precisa de construtor para o caso comum.

### 9.2 Enum: começa em 1, a menos que zero seja o default desejado

:::note[Regra]

Escrevo `Add Operation = iota + 1`, deixando o zero reservado para "não definido". A exceção é quando o zero value é o comportamento padrão bom, como em `LogToStdout = iota`.

:::

O [Uber](https://github.com/uber-go/guide#start-enums-at-one) lembra que variáveis começam em zero, então um enum em 0 não distingue "nunca setado" de "primeiro valor". Como complemento, enum com valor não-zero ganha um método `String()` ([Effective Go](https://go.dev/doc/effective_go#constants)).

```go title="enum.go"
type Operation int

const (
	Add Operation = iota + 1
	Subtract
	Multiply
)

// Add=1, Subtract=2, Multiply=3 — 0 = não definido.
```

### 9.3 Prefira definição a type alias

:::note[Regra]

Uso `type T1 T2`, uma nova definição. O alias `type T1 = T2` fica só para migração.

:::

O [Google decisions](https://google.github.io/styleguide/go/decisions#type-aliases) explica que a definição permite métodos e evolui, enquanto o alias congela a identidade do tipo.

### 9.4 `any` no lugar de `interface{}`

:::note[Regra]

Código novo usa `any`, e não `interface{}`.

:::

O [Google decisions](https://google.github.io/styleguide/go/decisions#use-any) prefere `any` porque ele comunica "qualquer tipo" sem parecer uma interface com método.

### 9.5 Não ponteirize por tamanho

:::note[Regra]

Passo valores por valor: struct pequena, string, int. Uso ponteiro para tipo grande ou mutável. Nunca `*string` ou `*int` só "para não copiar". A exceção é protobuf, que exige ponteiro.

:::

O [Google decisions](https://google.github.io/styleguide/go/decisions#pass-values) observa que ponteiro por tamanho economiza uma cópia e cria um nil-check desnecessário.

### 9.6 Receiver: valor ou ponteiro

:::note[Regra]

Método que muta usa ponteiro. Método que não muta e tem tipo pequeno usa valor. Tipo com mutex ou campo não copiável exige ponteiro. Mantenho consistência entre os métodos do mesmo tipo e, na dúvida, uso ponteiro.

:::

Valem o [Uber](https://github.com/uber-go/guide#receivers-and-interfaces) e o [Google decisions](https://google.github.io/styleguide/go/decisions#receiver-type). Valor dentro de map não é endereçável, então método de ponteiro não compila em `m[k].Write()`; um map de ponteiro resolve. Método de valor é chamável em valor e em ponteiro; método de ponteiro só em ponteiro ou valor endereçável.

### 9.7 Genéricos só quando cumprem requisito

:::note[Regra]

Uso tipo paramétrico quando há necessidade real, como coleções e algoritmos sobre tipos. Nomeio `T`, `K` e `V`, documento APIs genéricas exportadas, e não construo DSL nem framework de asserção em cima de generics.

:::

O [Google decisions](https://google.github.io/styleguide/go/decisions#generics) alerta contra uso prematuro: com um único tipo em jogo, prefira código concreto.

:::tip[Regra prática]

Desenhe o zero value primeiro; se ele serve, o construtor vira opcional.

:::

## Parte 10 — Panic, init, exit

### 10.1 Quase nunca `panic`

:::note[Regra]

Erro normal volta como `error`, e quem chama decide. `panic` fica para invariante irreversível, como nil deref, ou para boot. Nunca uso `recover` só para "não derrubar o programa".

:::

É o maior contraste entre o [Effective Go](https://go.dev/doc/effective_go#panic) e os guias modernos. O [Uber](https://github.com/uber-go/guide#dont-panic) lembra que panic em produção é fonte de cascata de falhas. O [Google](https://google.github.io/styleguide/go/best-practices#checks-and-panics) vai além: recuperar panic para evitar crash significa continuar rodando com estado possivelmente corrompido, e o guia chama o `recover` do `net/http` de "erro histórico".

```go title="panic.go"
// Errado: panic para erro que o chamador deveria decidir.
func connect() {
	conn, err := dial()
	if err != nil {
		panic(err)
	}
}

// Certo: erro sobe.
func connect() (*Conn, error) {
	conn, err := dial()
	if err != nil {
		return nil, fmt.Errorf("dial: %w", err)
	}
	return conn, nil
}
```

### 10.2 `Must*` para boot, não para handler

:::note[Regra]

Helper `Must*`, como `template.Must` e `regexp.MustCompile`, só serve para inicialização de variável de pacote ou valor em tabela de teste. Nunca dentro de um handler de request.

:::

Segundo o [Google decisions](https://google.github.io/styleguide/go/decisions#must-functions), no boot ainda não há request para responder; no handler, um `Must` derruba o processo por causa de um input do usuário.

### 10.3 Invariante quebrada: `log.Fatal`, não `panic`

:::note[Regra]

Condição impossível que impede o programa de continuar vira `log.Fatal` com mensagem acionável, não `panic`.

:::

O [Google](https://google.github.io/styleguide/go/best-practices#checks-and-panics) explica que os deferreds rodam durante o unwinding do `panic` e podem corromper ou travar. Uso `log.Exit` para falha de init em `main`, com instrução de correção.

### 10.4 `init()` é último recurso

:::note[Regra]

Evito `init`. Se for inevitável, ele é determinístico, sem I/O, sem acessar env, cwd ou args, sem depender da ordem de outros `init`s e sem goroutine. A lógica real vai para um helper chamado por `main()` ou pelo construtor.

:::

O [Uber](https://github.com/uber-go/guide#avoid-init) chama isso de "init magic": em biblioteca, é impossível de testar e raciocinar. As exceções aceitas são registro de driver (`database/sql`), registry de encoding e expressão complexa de atribuição única.

### 10.5 `os.Exit`/`log.Fatal` só em `main()`, uma vez

:::note[Regra]

Função que falha retorna erro, e `main()` faz `if err := run(); err != nil { log.Fatal(err) }`. Um único ponto de exit.

:::

O [Uber](https://github.com/uber-go/guide#exit-in-main) lista os problemas de sair em qualquer função: fluxo não óbvio, função que mata o `go test` quando chamada, e `defer` de cleanup pulado. Extrair `run() error` testa a lógica sem matar o teste.

```go title="main.go"
func main() {
	if err := run(); err != nil {
		log.Fatal(err)
	}
}

func run() error {
	// ... lógica real, retorna erro
	return nil
}
```

### 10.6 Goroutine com fim previsível

:::note[Regra]

Toda goroutine tem condição de saída — channel fechado, `context` ou `WaitGroup` — e um meio de esperar por ela. Nada de fire-and-forget sem dono, e nenhuma goroutine em `init`.

:::

O [Uber](https://github.com/uber-go/guide#dont-fire-and-forget-goroutines) e o [Google](https://google.github.io/styleguide/go/decisions#goroutine-lifetimes) explicam que goroutine vazada segura memória e recursos para sempre, porque o GC não coleta goroutine bloqueada. Para esperar, uso `WaitGroup` quando são várias e `done := make(chan struct{}); <-done` quando é uma.

```go title="goroutine.go"
stop := make(chan struct{})
done := make(chan struct{})

go func() {
	defer close(done)
	ticker := time.NewTicker(delay)
	defer ticker.Stop()
	for {
		select {
		case <-ticker.C:
			flush()
		case <-stop:
			return
		}
	}
}()

// Em outro ponto:
close(stop)
<-done // espera sair
```

### 10.7 Prefira função síncrona

:::note[Regra]

A função nasce síncrona, e quem chama decide se ela roda em uma goroutine.

:::

Segundo o [Google decisions](https://google.github.io/styleguide/go/decisions#synchronous-functions), adicionar `go` na chamada é trivial, mas remover concorrência desnecessária depois é difícil.

:::tip[Regra prática]

`panic` é para bug, não para fluxo; e `exit` é um só, no topo.

:::

## Parte 11 — Interfaces

### 11.1 Interface por valor, nunca ponteiro

:::note[Regra]

Parâmetro e retorno de interface usam o valor da interface, como `io.Reader`, e nunca `*io.Reader`. A interface já tem dois ponteiros internos; se o método precisa mutar, o dado embaixo é que é ponteiro.

:::

O [Uber](https://github.com/uber-go/guide#pointers-to-interfaces) diz que ponteiro para interface é quase sempre erro: só o dado subjacente decide o endereçamento.

### 11.2 Verifique compliance em compile-time

:::note[Regra]

Tipo exportado cujo contrato exige uma interface ganha `var _ http.Handler = (*Handler)(nil)`. Uso isso só onde não existe conversão estática que já garantiria.

:::

O [Uber](https://github.com/uber-go/guide#verify-interface-compliance) mostra que a linha quebra o build no instante em que o contrato muda. O lado direito é o zero value: `nil` para ponteiro e `T{}` para struct.

### 11.3 Interface sob demanda, do lado de quem consome

:::note[Regra]

Crio interface quando há necessidade real, como dois ou mais implementadores, quebra de ciclo ou protocolo. O consumidor define; o produtor só exporta interface quando ela **é** o produto. Nada de interface reflexiva "service/repository".

:::

O [Google best-practices](https://google.github.io/styleguide/go/best-practices#interfaces) explica que abstração prematura aumenta o custo de manutenção sem benefício. Aceito interface e retorno struct concreto; as exceções são `error`, factory e tipos `io.Reader`-like.

```go title="interface.go"
// Certo: interface pequena, do lado de quem consome.
type Storer interface {
	Store(ctx context.Context, key string, v []byte) error
}

func NewService(st Storer) *Service { ... } // retorna struct
```

### 11.4 Interface de um método se chama pelo verbo + `-er`

:::note[Regra]

Escrevo `type Reader interface { Read(...) }`. O nome deriva do método canônico.

:::

O [Effective Go](https://go.dev/doc/effective_go#interface-names) mostra que esse nome é reconhecível e curto.

:::tip[Regra prática]

Interface pequena, definida por quem consome e aceita por valor.

:::

## Parte 12 — Concorrência

### 12.1 Canal: capacidade 0 ou 1

:::note[Regra]

O canal nasce sem buffer. Tamanho 1 precisa de justificativa, e buffer maior só com razão forte, como backpressure ou throughput medido.

:::

O [Uber](https://github.com/uber-go/guide#channel-size-is-one-or-none) lembra que "ought to be enough for anybody" (`make(chan int, 64)`) não é design: buffer esconde acoplamento e bloqueio.

### 12.2 Direção de canal na assinatura

:::note[Regra]

A assinatura declara `<-chan` ou `chan<-` quando o uso é de leitura ou de escrita, e o compilador pega o uso errado.

:::

O [Google best-practices](https://google.github.io/styleguide/go/best-practices#channel-direction) mostra que isso expressa ownership e pega bug em compile-time.

### 12.3 Context: primeiro parâmetro; nunca campo de struct

:::note[Regra]

Escrevo `func Run(ctx context.Context, ...)`, com o contexto primeiro. Nunca em struct e nunca como tipo customizado.

:::

Segundo o [Google decisions](https://google.github.io/styleguide/go/decisions#contexts), o contexto é fluxo de chamada, não estado do objeto. Um tipo customizado de context quebra refactor automatizado.

### 12.4 Atômicos: stdlib tipado

:::note[Regra]

Uso `sync/atomic` com os tipos tipados, como `atomic.Bool` e `atomic.Int64`, sempre por método (`Load`, `Swap`) e nunca por leitura crua.

:::

O [Uber](https://github.com/uber-go/guide#use-gouberorgatomic) recomendava `go.uber.org/atomic` porque o `sync/atomic` cru permite `f.running == 1 // race!`. A stdlib ganhou tipos tipados equivalentes, então uso a stdlib, com menos dependência, mantendo a disciplina: **atômico só se lê e escreve por método atômico**.

```go title="atomic.go"
type foo struct {
	running atomic.Bool
}

func (f *foo) start() {
	if f.running.Swap(true) {
		return // já está rodando
	}
	// inicia...
}

func (f *foo) isRunning() bool {
	return f.running.Load() // nunca f.running cru
}
```

### 12.5 Defer para liberar recurso

:::note[Regra]

Lock e arquivo são liberados por `defer` imediatamente após serem adquiridos. O custo do `defer` é desprezível fora de uma função de nanossegundos.

:::

O [Uber](https://github.com/uber-go/guide#defer-to-clean-up) mostra que o `defer` garante a liberação em todo caminho de return e mantém o open e o close próximos.

```go title="defer.go"
p.Lock()
defer p.Unlock()

if p.count < 10 {
	return p.count // unlock garantido
}
p.count++
return p.count
```

:::tip[Regra prática]

Concorrência sem dono é leak: todo canal e toda goroutine têm fim.

:::

## Parte 13 — Testes

### 13.1 Stdlib `testing` primeiro

:::note[Regra]

O padrão é a stdlib `testing`, com mensagem no formato `função(%v) = %v, want %v`. Não uso biblioteca de asserção como dogma.

:::

O [Google decisions](https://google.github.io/styleguide/go/decisions#assert) argumenta que libs de asserção abortam cedo, omitem contexto e fragmentam a experiência de debug; o Uber usa testify nos exemplos. Minha régua: stdlib primeiro, para sentir a linguagem; em um time com convenção testify estabelecida, sigo a convenção local.

```go title="teste.go"
func TestSplitHostPort(t *testing.T) {
	host, port, err := net.SplitHostPort("192.0.2.0:8000")
	if err != nil {
		t.Fatalf("SplitHostPort erro inesperado: %v", err)
	}
	if want := "192.0.2.0"; host != want {
		t.Errorf("SplitHostPort host = %q, want %q", host, want)
	}
	if want := "8000"; port != want {
		t.Errorf("SplitHostPort port = %q, want %q", port, want)
	}
}
```

### 13.2 Tabela quando o corpo repete

:::note[Regra]

Vários casos da mesma lógica viram uma tabela com `t.Run` e nome descritivo por caso. A convenção é slice `tests`, elemento `tt`, campos `give` e `want`. Um caso só vira teste simples, e o subteste não leva condicional complexo; quando chega nesse ponto, quebro em testes separados.

:::

O [Uber](https://github.com/uber-go/guide#test-tables) mostra que a tabela reduz duplicação e faz cada falha identificar o caso. Complexidade dentro da tabela, o "test depth", torna a falha ilegível.

```go title="tabela.go"
tests := []struct {
	give     string
	wantHost string
	wantPort string
}{
	{give: "192.0.2.0:8000", wantHost: "192.0.2.0", wantPort: "8000"},
	{give: "1:8", wantHost: "1", wantPort: "8"},
}

for _, tt := range tests {
	t.Run(tt.give, func(t *testing.T) {
		host, port, err := net.SplitHostPort(tt.give)
		if err != nil {
			t.Fatalf("erro inesperado: %v", err)
		}
		if host != tt.wantHost {
			t.Errorf("host = %q, want %q", host, tt.wantHost)
		}
		if port != tt.wantPort {
			t.Errorf("port = %q, want %q", port, tt.wantPort)
		}
	})
}
```

### 13.3 Helper de teste marca falha no caller

:::note[Regra]

Helper de setup que falha chama `t.Helper()` e `t.Fatalf` dizendo o que e quanto. Helper de asserção que recebe `*testing.T` só para falhar eu evito: a validação fica no `Test`, ou o helper retorna `error`.

:::

O [Google best-practices](https://google.github.io/styleguide/go/best-practices#test-functions) mostra que `t.Helper()` redireciona a falha para a linha do caller. Um helper de asserção esconde contexto e fragmenta a mensagem.

### 13.4 `t.Error` por padrão; `t.Fatal` só quando não dá para continuar

:::note[Regra]

Falha de comparação usa `t.Errorf`, que continua e mostra todas. Falha de setup ou decodificação que invalida o resto usa `t.Fatalf`. Goroutine separada nunca chama `FailNow`: usa `t.Errorf` e retorna.

:::

Segundo o [Google](https://google.github.io/styleguide/go/best-practices#tests), `t.Error` reporta todas as falhas de uma rodada, enquanto um `t.Fatal` prematuro esconde as demais.

### 13.5 Teste sem estado global compartilhado

:::note[Regra]

Dados caros de setup são carregados pelo teste que precisa, como `mustLoadDataset(t)`, e não em `init()` de pacote de teste. `TestMain` só quando **todo** teste precisa do setup caro.

:::

O [Google best-practices](https://google.github.io/styleguide/go/best-practices#test-setup) explica que setup em `init` quebra o filtro `-run` e impõe custo a quem não precisa.

### 13.6 Compare estrutura inteira, não campo a campo

:::note[Regra]

Struct ou resultado composto pede comparação profunda, como `cmp.Diff`, e não uma série de `if` por campo.

:::

O [Google decisions](https://google.github.io/styleguide/go/decisions#compare-full-structures) mostra que a comparação profunda acha a diferença que a comparação campo a campo esquece. Para erro, testo a semântica com `errors.Is`, nunca o texto.

### 13.7 Falha útil: `got`/`want`, com função e input

:::note[Regra]

A mensagem inclui função, input e valores, como `SplitHostPort(%q) = %q, want %q`. O valor real vem antes do esperado ("got"/"want"), e struct grande usa `cmp.Diff`.

:::

O [Google decisions](https://google.github.io/styleguide/go/decisions#useful-test-failures) resume o objetivo: o teste deve ser diagnosticável sem ler o código-fonte. Sem isso, a falha vira arqueologia.

### 13.8 Test doubles e pacote de teste

:::note[Regra]

Test double vive em um pacote `<produto>test`, como `creditcardtest`. Nomeio `Stub` quando há um só, ou pelo comportamento, como `AlwaysDeclines`. Teste black-box usa pacote `_test`.

:::

O [Google best-practices](https://google.github.io/styleguide/go/best-practices#naming-doubles) observa que o contexto do pacote já diz o domínio; `StubService` e `StubCreditCardService` repetem o que o import já diz.

### 13.9 `t.Cleanup`, `t.Setenv`, `t.Parallel`

:::note[Regra]

Recurso com teardown usa `t.Cleanup`; variável de ambiente usa `t.Setenv`, que restaura sozinho; `t.Parallel` isola os testes. Nunca uso `t.Fatal` em goroutine separada.

:::

O [Google best-practices](https://google.github.io/styleguide/go/best-practices#test-setup) mostra que o setup escopado ao teste que precisa evita vazamento de estado entre casos. E `t.Fatal` fora da goroutine do teste chama `FailNow` no lugar errado.

:::tip[Regra prática]

Teste bom falha dizendo o que quebrou, com que input e qual era o esperado.

:::

## Parte 14 — Funções e parâmetros

### 14.1 Assinatura curta; opções quando cresce

:::note[Regra]

Assinatura com três ou mais argumentos opcionais vira struct de opções ou variadic options. O contexto nunca entra no struct de opções: ele fica como primeiro parâmetro.

:::

O [Uber](https://github.com/uber-go/guide#functional-options) e o [Google](https://google.github.io/styleguide/go/best-practices#function-argument-lists) mostram que uma chamada com cinco parâmetros posicionais é ilegível, enquanto options crescem sem quebrar os callers.

```go title="options.go"
// Errado: 3 argumentos sempre obrigatórios.
func Open(addr string, cache bool, logger *zap.Logger) (*Conn, error)

// Certo: só o que o caller quer.
func Open(addr string, opts ...Option) (*Conn, error)

// Uso:
db.Open(addr)
db.Open(addr, db.WithLogger(log), db.WithCache(false))
```

### 14.2 Opções: interface com método unexported > closure

:::note[Regra]

Option é `type Option interface { apply(*options) }`, com `WithX` retornando o tipo. Closure, ou seja, função que seta o campo, é a segunda escolha.

:::

Segundo o [Uber](https://github.com/uber-go/guide#functional-options), um valor de opção por interface pode ser comparado, mockado e ganhar `String()`; a closure não. Registro que, para projeto pequeno, closure basta; sigo a forma do Uber quando a API é pública.

### 14.3 Evite parâmetro nu

:::note[Regra]

Booleano ou estado que não se explica na chamada vira um tipo nomeado com constante, ou recebe um comentário como `/* isLocal */`.

:::

O [Uber](https://github.com/uber-go/guide#avoid-naked-parameters) mostra que `printInfo("foo", true, true)` não diz o que é cada `true`. Um tipo como `Region` ou `Status` também permite mais estados no futuro.

### 14.4 Raw string para evitar escape

:::note[Regra]

String com aspas, barra ou multilinha usa backtick: `` `unknown error:"test"` ``, e não `"unknown name:\"test\""`.

:::

O [Uber](https://github.com/uber-go/guide#use-raw-string-literals-to-avoid-escaping) lembra que o escape manual é difícil de ler e de acertar.

### 14.5 Formato de Printf como `const`

:::note[Regra]

Format string fora de um literal é `const`. Função estilo printf que eu crio termina em `f`, como `Wrapf`, para o `go vet` achar.

:::

Segundo o [Uber](https://github.com/uber-go/guide#format-strings-outside-printf), o `go vet` só analisa estaticamente a format string de uma `const`.

### 14.6 Resultados nomeados com moderação

:::note[Regra]

Nomeio resultados quando os tipos não bastam, como em `(left, right *Node, err error)`, quando o caller precisa agir sobre um deles (`ctx, cancel`) ou quando o valor muda em um closure `defer`. Nomear só para usar naked return em função grande, não.

:::

O [Google decisions](https://google.github.io/styleguide/go/decisions#named-result-parameters) observa que o naked return em função grande esconde o que está sendo retornado.

:::tip[Regra prática]

Assinatura curta; o que é opcional ganha nome por meio de option.

:::

## Parte 15 — Strings e tempo

### 15.1 Prefira `strconv` a `fmt` no hot path

:::note[Regra]

Conversão de primitivo para string usa `strconv.Itoa` e `FormatInt`. O `fmt` fica para formatos compostos.

:::

O benchmark da [performance do Uber](https://github.com/uber-go/guide#prefer-strconv-over-fmt) mostra 64ns com 1 alloc no `strconv`, contra 143ns com 2 allocs no `fmt`. Só no hot path.

### 15.2 Não reconverta string fixa em bytes no loop

:::note[Regra]

Faço `data := []byte("...")` uma vez, fora do loop.

:::

Segundo a [performance do Uber](https://github.com/uber-go/guide#avoid-repeated-string-to-byte-conversions), isso custa 3,25ns por iteração, contra 22,2ns quando a conversão fica dentro do loop.

### 15.3 Construção de string: ferramenta certa para o caso

:::note[Regra]

Poucas concatenações usam `+`. Formatação usa `fmt.Sprintf`. Quando o destino é um `io.Writer`, uso `fmt.Fprintf`. Montagem em loop usa `strings.Builder`, que é linear em vez de quadrático. Template complexo usa `text/template`.

:::

Vale o [Google best-practices](https://google.github.io/styleguide/go/best-practices#string-concatenation).

### 15.4 Hora é `time.Time`/`time.Duration`

:::note[Regra]

Instante é `time.Time` e período é `time.Duration`. Comparo por método (`Before`, `Equal`), nunca por `int`. A assinatura aceita `time.Duration` para o caller escrever `10 * time.Second`. Em formato externo sem suporte, como JSON, o campo leva a unidade no nome (`IntervalMillis`), e timestamp vira string RFC 3339.

:::

O [Uber](https://github.com/uber-go/guide#use-time-to-handle-time) lembra que as suposições sobre tempo são falsas: dia nem sempre tem 24h, mês nem sempre tem 30 dias. `AddDate(0,0,1)` é o próximo dia de calendário, e `Add(24*time.Hour)` é o instante 24h depois; são intenções diferentes.

```go title="time.go"
func poll(delay time.Duration) { // caller: poll(10 * time.Second)
	// ...
}

// Errado: int sem unidade.
func poll(delay int) // poll(10) — segundos? milissegundos?
```

### 15.5 Formate string com `%q`

:::note[Regra]

Para imprimir uma string entre aspas, uso `%q` em vez de concatenar `"\"" + s + "\""`.

:::

Segundo o [Google decisions](https://google.github.io/styleguide/go/decisions#use-q), uma diretiva faz o escape correto, enquanto montar aspas na mão é mais verboso e erra em caractere especial.

:::tip[Regra prática]

Use o tipo certo, como `time.Duration`, e não um número com a unidade embutida no nome.

:::

## Parte 16 — Importação e dependências

### 16.1 Alias quando o nome do pacote difere do caminho

:::note[Regra]

O alias é obrigatório quando o nome do pacote difere do último elemento do path, como `client "example.com/client-go"`. Evito alias nos outros casos, salvo colisão direta.

:::

O [Uber](https://github.com/uber-go/guide#import-aliasing) lembra que o nome do pacote é como o caller se refere a ele; sem alias, ele engana.

### 16.2 Import `.` proibido; `_` restrito

:::note[Regra]

Import com ponto (`.`) é proibido. Import de side-effect (`_`) só em `main` ou em teste, quando o efeito é o objetivo.

:::

Segundo o [Google decisions](https://google.github.io/styleguide/go/decisions#imports), o `.` esconde a origem dos símbolos e o `_` em biblioteca registra um global escondido de quem importa.

### 16.3 Stdlib primeiro, dependência por problema real

:::note[Regra]

Antes de adicionar uma dependência, confirmo que a stdlib não resolve. Dependência nova é superfície de manutenção, de segurança e de compatibilidade.

:::

Vale o princípio de [least mechanism do Google guide](https://google.github.io/styleguide/go/guide#least-mechanism).

### 16.4 Pacotes coesos, não gigantes

:::note[Regra]

O pacote reúne o que é usado junto: se o cliente precisa importar dois pacotes para usar um, provavelmente é um só. Evito pacote gigante e a convenção "um tipo por arquivo"; cada arquivo deve ser localizável pelo conteúdo.

:::

O [Google best-practices](https://google.github.io/styleguide/go/best-practices#package-size) lembra que o godoc mostra o pacote em uma página, então a coesão certa reduz cerimônia sem poluir a API pública.

### 16.5 Import de proto com `pb`/`grpc`

:::note[Regra]

Proto gerado importa com sufixo `pb` para proto ou `grpc` para gRPC. Removo o `_` do nome local e prefiro um nome descritivo.

:::

O [Google best-practices](https://google.github.io/styleguide/go/best-practices#import-protos) explica que proto é cross-language, então a convenção de rename é estável e legível no call site.

:::tip[Regra prática]

Toda dependência é dívida até provar que resolve o problema.

:::

## Parte 17 — Linting e ferramentas

:::note[Regra]

Minha base de linters é `errcheck`, para erros tratados; `goimports`, para formatação e imports; `govet`, para erros comuns; `staticcheck`, para análise estática; e `revive`, para estilo, como sucessor do golint. O runner é o `golangci-lint`.

:::

O [Uber linting](https://github.com/uber-go/guide#linting) mostra que o valor não está em um linter específico, mas em **lintar consistentemente** no codebase. Minha régua pessoal: quando um linter discorda de uma regra documentada aqui, ele ganha um `//nolint` com referência à seção, para a exceção ficar rastreável e não mudar em silêncio.

:::tip[Regra prática]

Configure uma vez, rode sempre; silencie exceção com referência, nunca sem.

:::

## Parte 18 — Quando quebro as próprias regras

Toda regra tem uma exceção legítima, e este guia registra onde:

- **Performance comprovada** com benchmark pode justificar um desvio. Documento o porquê no código e cubro com teste.
- **Código de demonstração**, como os exemplos do blog, prioriza clareza pedagógica sobre dogmatismo.
- **Consistência local**: em pacote com convenção estabelecida e nenhuma regra objetiva aplicável, sigo o vizinho.
- **Contrato com time**: se o time tem um guia próprio que diverge, como testify, o guia do time vence **dentro daquele time**, e eu documento a divergência ao público.

A régua final é o princípio 1.1: o código está claro? Se está, a regra cumpriu o papel.

## Parte 19 — Idiomas modernos

### 19.1 `slices` e `maps` antes de loop manual

:::note[Regra]

Uso `slices.Clone`, `slices.Contains`, `slices.Sort` e `maps.Clone` no lugar de loop manual quando existe equivalente, desde o Go 1.21.

:::

A stdlib é tipada e testada, então sobra menos código e menos bug.

### 19.2 `sync.OnceValue`/`OnceFunc`

:::note[Regra]

Inicialização lazy e única usa `sync.OnceValue` ou `OnceFunc`, do Go 1.21, em vez de `sync.Once` manual.

:::

Isso reduz o boilerplate e dispensa a variável capturada para guardar o resultado.

### 19.3 Variável de laço é por iteração (Go 1.22)

:::note[Regra]

Desde o Go 1.22 cada iteração tem a sua variável, então capturar em goroutine ou closure não exige mais `x := x`. Mesmo assim, não relaxo o resto: goroutine continua precisando de dono (10.6).

:::

A mudança removeu o bug clássico de captura, mas o requisito de ciclo de vida continua valendo.

### 19.4 `min`/`max` e `strings.Cut`

:::note[Regra]

Uso `min(a, b)` e `max(a, b)`, do Go 1.21, no lugar de um `if`. E uso `strings.Cut` no lugar de `SplitN` quando quero "antes e depois".

:::

Builtins e stdlib cobrem o caso comum com menos ruído sintático.

:::tip[Regra prática]

Antes de escrever loop ou `Once` manual, veja se a stdlib já resolve.

:::

## Apêndice A — As três fontes

| Guia | Forma | Normativo | Papel |
| --- | --- | --- | --- |
| **Effective Go** | Ensaio único, em prosa | Não | Ensinar o idioma; baseline comum da comunidade |
| **Google guide** | Documento canônico | Sim | Princípios + regras centrais (todos) |
| **Google decisions** | Decisões estilo RFC | Sim | Por quê de cada regra (revisores de readability) |
| **Google best-practices** | Padrões situacionais | Não | Recomendações com trade-offs (interessados) |
| **Uber guide** | Arquivo único, tabelas Bad/Good | Sim (na Uber) | Checklist pragmático de review |

O Effective Go é o alicerce. O Google é hierárquico: o `guide` manda, o `decisions` explica, o `best-practices` sugere. O Uber é a régua prática de code review.

## Apêndice B — Matriz de origem

Cada regra nasceu em um guia específico. Esta é a matriz de origem, com o "vencedor" de cada tema e o motivo pelo qual ele ganha para manutenção e leitura:

| Tema | Fonte escolhida | Por que ganha |
| --- | --- | --- |
| Formatação | Effective Go / gofmt | Máquina decide; zero discussão em PR |
| Linha longa | Google (sem teto rígido) | Refatorar > fatiar linha; quebra antes de indentação confunde |
| Nomes / não repetição | Google | Regra mais sistematizada; legibilidade direta |
| Getters / `-er` / MixedCaps | Effective Go + Google | Consenso comunitário, reconhecível |
| Erros: estrutura, `%w`, mensagem | Google decisions | Cadeia e matching previsíveis; base de manutenção |
| Erros: sem "failed to", handle-once | Uber | Logs limpos; anti-padrão de duplicação |
| `panic`/`recover`/`Must*` | Google | Mais rigoroso; protege contra estado corrompido |
| `init`/estado global | Google + Uber | Determinismo e teste isolado |
| Struct, mutex, field tags, map | Uber | Regra prática de review |
| nil slice / copy na fronteira | Uber + Google | Evita bug de aliasing e distinção nil/vazio |
| Performance | Uber (hot path) | Benchmarks reais, escopo restrito |
| Interfaces / ports | Google | Sob demanda + consumer-side; base hexagonal |
| Concorrência / goroutines | Uber + Google | Ciclo de vida explícito |
| Contexto | Google | Regra dura; nunca em struct |
| Testes | Google (base) + Uber (tabela) | Veredito na seção 13.1 |
| Functional options | Uber | Cresce sem quebrar chamada |
| Genéricos | Google decisions | Uso cauteloso, sem DSL |

Onde Uber e Google colidem sem vencedor claro de manutenção, a seção correspondente registra os dois lados e a minha escolha. Nenhuma regra entra aqui por tradição ou por ser "a da empresa X".
