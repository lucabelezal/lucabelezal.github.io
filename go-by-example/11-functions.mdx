Se você reparar em código Go real, vai notar uma coisa: **tudo é feito com funções**. Não há classes estáticas, nem métodos globais, nem herança — há funções. Funções são o principal mecanismo de organização, abstração e reuso da linguagem. Nesta página você vai ver a anatomia de uma função e, mais importante, o que torna Go "meio funcional": funções são **valores**, que podem ser guardados em variáveis, passados como argumento e devolvidos por outras funções.

## Funções são cidadãs de primeira classe

O traço mais importante de funções em Go não é a sintaxe — é que uma função é um **valor comum**, com um tipo. Você pode guardá-la numa variável:

```go
dobro := func(n int) int { return n * 2 }
fmt.Println(dobro(21)) // 42
```

`func(n int) int { ... }` é uma **função anônima** (sem nome) e `dobro` é uma variável cujo tipo é `func(int) int`. A sintaxe de tipo de função espelha a assinatura: `func(parâmetros) retorno`.

Por serem valores, funções podem ser passadas para outras funções, devolvidas por funções e comparadas com `nil`. É exatamente isso que dá à linguagem um "pé" no paradigma funcional — sem exigir que você programe funcionalmente.

## Funções como argumento (callbacks)

Passar uma função para outra é o padrão de **callback**: você entrega o "o quê fazer" e a função chamadora decide "quando fazer". Em Go isso aparece o tempo todo — ordenação com critério próprio, handlers HTTP, middlewares. Veja um exemplo concreto:

<CodeExplanation

import "fmt"

func transformar(nums []int, fn func(int) int) []int {
    resultado := make([]int, len(nums))

        resultado[i] = fn(n)
    }
    return resultado
}

func main() {
    dobro := func(n int) int { return n * 2 }
    numeros := []int{1, 2, 3}
    fmt.Println(transformar(numeros, dobro))
}`}

## Exportada × interna (pública × privada)

Uma função é **exportada** se o nome começa com **maiúscula** e fica visível para outros packages; começa com **minúscula**, é interna ao package. Não existe palavra-chave `public`/`private` — a caixa do identificador decide.

As funções `plus` e `plusPlus` deste exemplo começam com minúscula: são internas ao package `main`, que não é importado por ninguém. A regra completa — e por que `NewProduct` é exportado — está em [Visibilidade e Packages](visibility-and-packages).

## Construtores: por que `New...`?

Go **não tem construtor**. Em Swift existe `init`, em Java o método com o nome da classe — em Go, nada disso. Não há palavra-chave de construção nem sobrecarga de função. Como então se cria um valor que precisa de regras?

Com uma função exportada que segue a convenção de nome `NewTipo`:

```go
type Conta struct {
    titular string
    saldo   float64
}

func NewConta(titular string, saldoInicial float64) Conta {
    return Conta{titular: titular, saldo: saldoInicial}
}
```

`NewConta` é só uma função — mas uma função com um **contrato**: concentra as regras de criação num único lugar. Se amanhã `Conta` passar a exigir validação (saldo não pode ser negativo) ou um campo novo, você muda `NewConta` e todos os pontos de criação ficam seguros. Esse padrão fica ainda mais importante quando os campos são internos, porque um literal `Conta{...}` com campos minúsculos não pode ser montado fora do package — assunto das páginas de [Structs](structs) e [Visibilidade e Packages](visibility-and-packages).

## O "pezinho funcional" de Go

Go não é uma linguagem funcional: não impõe imutabilidade e não tem funções de alta ordem na gramática. Mas como funções são valores, o **estilo funcional aparece naturalmente**:

- callbacks para customizar comportamento (como `transformar` acima);
- funções que **devolvem funções**, para criar variações de um comportamento — o coração de [Closures](closures);
- middlewares HTTP, que recebem um handler e devolvem outro.

Ao mesmo tempo, Go **não tem sobrecarga nem parâmetros com valor padrão**. Quando você precisa de uma função que aceite combinações diferentes de argumentos, as saídas da linguagem são: parâmetros variádicos (próximas páginas), o padrão `New...` e *functional options*. Essa ausência não é acidente — força a API a ser explícita e legível.

## Armadilhas comuns

- **Esperar sobrecarga**: dois `func soma(...)` com assinaturas diferentes não compilam no mesmo package. Se precisa de "mesma lógica para tipos diferentes", a resposta é [Generics](generics).
- **Esperar parâmetro opcional**: `func log(msg string, nivel = "info")` não existe. Para opcional, use variádicos ou um parâmetro de configuração.
- **Chamar a função em vez de passá-la**: no callback, `transformar(numeros, dobro())` passa o *resultado* da chamada (um `int`), não a função — erro de tipo.
- **Passagem por valor**: `plus` recebe **cópias** de `a` e `b`. Mudar um parâmetro dentro da função não afeta a variável do chamador. Para modificar o original, você precisará de [Ponteiros](pointers).
- **Esquecer o `return`**: função com retorno declarado que não retorna em todos os caminhos não compila.

## Pratique

1. **Reproduza**: rode `functions.go` e `callback.go` e confira as saídas.
2. **Modifique**: reescreva `plusPlus` para **compor** chamadas de `plus` (`plus(plus(a, b), c)`) — funções que chamam funções. Depois passe uma função anônima direto para `transformar` (sem variável intermediária).
3. **Aplique**: escreva `aplicarEmCada(nums []int, fn func(int))` que chama `fn` para cada elemento, e use-a para imprimir apenas os pares. Você acabou de montar um *forEach* como o de linguagens funcionais.
