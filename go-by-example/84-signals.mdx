O SO se comunica com processos por **sinais**: `Ctrl+C` envia `SIGINT`, `kill` envia `SIGTERM`, e um processo que não trata morre na hora. Para um servidor, morrer na hora é ruim — você quer **parar com elegância**: terminar o request em andamento, fechar conexões, salvar estado. O `os/signal` captura esses sinais e o padrão moderno é um `signal.NotifyContext`: um context que é cancelado quando o sinal chega.

## O padrão de graceful shutdown

No mundo real, o sinal não encerra o programa direto — ele dispara o **shutdown**:

```go
func main() {
    ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
    defer stop()

    srv := &http.Server{Addr: ":8090", Handler: mux}

    go func() {
        <-ctx.Done()                       // sinal chegou
        ctxShutdown, cancel := context.WithTimeout(context.Background(), 10*time.Second)
        defer cancel()
        srv.Shutdown(ctxShutdown)          // para de aceitar e espera requests (página [Servidor HTTP](http-server))
    }()

    log.Fatal(srv.ListenAndServe())
}
```

O `SIGTERM` (default do `docker stop`/orquestradores) e o `SIGINT` (`Ctrl+C`) são os dois sinais de "pare"; tratar os dois cobre dev e prod. Por isso `kill <pid>` sem flag manda SIGTERM — e o processo tratá-lo significa que o container para de forma limpa.

## Sinais comuns que importam

| Sinal | Origem | Significado |
|---|---|---|
| `SIGINT` | `Ctrl+C` no terminal | Interrupção |
| `SIGTERM` | `kill`, orquestradores | Pede para terminar (o padrão) |
| `SIGHUP` | terminal fechou / reload | Recarregar config ou morrer |
| `SIGKILL` | `kill -9` | Mata — **não dá para capturar** |
| `SIGQUIT` | `Ctrl+\` | Termina e despeja stack (dump) |

`SIGKILL` e `SIGSTOP` não podem ser capturados — não adianta tratar. O resto, `NotifyContext` cobre.

## Em código real

- **Servidores**: parar de aceitar novas conexões + `Shutdown` com timeout (requests em voo terminam).
- **Workers**: o `ctx.Done()` sinaliza as goroutines para terminarem — o padrão das quatro perguntas de [Ciclo de Vida de Goroutines](goroutine-lifecycle).
- **CLIs**: `Ctrl+C` interrompe uma operação longa de forma limpa.
- Filhos de `exec.CommandContext` (página [Criando Processos](spawning-processes)) morrem junto quando o context cancela.

## Armadilhas comuns

- **`stop()` esquecido**: sem `defer stop()`, o programa continua capturando o sinal (e o `Ctrl+C` deixa de matá-lo). Restaure sempre.
- **Tratar só `SIGINT`**: em prod o orquestrador manda `SIGTERM`. Trate os dois.
- **Achar que `SIGKILL` dá para tratar**: não. `kill -9` é o último recurso; o graceful shutdown é para `TERM`/`INT`.
- **Fazer trabalho longo no handler do sinal sem timeout**: o `Shutdown` pode travar esperando. Timeout no `ctxShutdown`.
- **Capturar sinal e não propagar**: se o sinal deve parar as goroutines, propague o `ctx` (não crie um `Background` novo no meio — página [Context](context)).

## Pratique

1. **Reproduza**: rode `signals.go` e envie `Ctrl+C`; depois rode em background e `kill -TERM <pid>` (mesma saída, sinal diferente).
2. **Modifique**: capture `SIGHUP` também e imprima qual sinal chegou usando `context.Cause`.
3. **Aplique**: integre o padrão ao [Servidor HTTP](http-server): suba o servidor, `Ctrl+C` e observe o shutdown — adicione um log em `srv.Shutdown`.
