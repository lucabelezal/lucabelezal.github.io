Na página anterior, o programa criou um **filho** e continuou vivo. `syscall.Exec` é o oposto: ele **substitui o processo atual** pelo programa dado — mesma PID, mesma identidade, mas o código Go some e o novo programa assume. É o mecanismo de `exec` do Unix, e o motivo de existir: programas wrapper que querem "virar" o alvo (um `ssh` que vira o shell, um init que vira o serviço).

## `exec.Command` × `syscall.Exec`

| | `os/exec.Command` (página anterior) | `syscall.Exec` |
|---|---|---|
| Resultado | Cria um **filho**; o Go continua | **Substitui** o processo; o Go acaba |
| PID | Novo PID | Mesmo PID |
| Retorno | Volta com output/código | Só retorna em erro |
| Uso | Rodar ferramentas e continuar | Wrappers que viram o alvo |

Regra: 99% dos casos querem `exec.Command` (você quer continuar e ver o resultado). `syscall.Exec` é para quando o programa **não deve voltar** — o sucessor assume o processo e herda stdin/stdout/stderr e o exit code naturalmente.

## Quando usar Exec de verdade

- **Wrappers de comando**: um `meu-git` que valida e então vira o `git` real — sinais e exit code do git passam direto.
- **`init`/supervisores** que executam o serviço final como o próprio processo.
- **Login shells**: o shell substitui a si mesmo pelo comando do usuário.
- Sinais: como o processo é o mesmo, `kill` chega direto no programa executado — diferente do filho, onde você gerencia a propagação (página [Sinais](signals)).

## Sobre `fork`

Go não expõe o `fork` clássico do Unix (criar uma cópia do processo). Na prática isso raramente falta: você tem **goroutines** (leves, dentro do processo) para concorrência, `exec.Command` para filhos e `syscall.Exec` para substituição — os três casos que o `fork`+`exec` cobria juntos.

## Armadilhas comuns

- **Passar o caminho errado**: `syscall.Exec` não busca no PATH. Use `exec.LookPath` antes.
- **Esquecer o nome na frente dos args**: `args[0]` deve ser o nome do programa (é o que o alvo vê como `argv[0]`).
- **Achar que o código continua depois**: se o `Exec` funciona, não há "depois". O código após a chamada só roda em caso de erro.
- **Usar `Exec` onde `Command` bastaria**: se você quer o resultado e seguir, `syscall.Exec` mata seu programa — escolha a ferramenta certa.
- **Semáforo de build**: `syscall.Exec` é Unix-only; para portabilidade, mantenha em arquivo com `//go:build unix`.

## Pratique

1. **Reproduza**: rode `execing-processes.go` e note que o `ls` roda com o mesmo PID (confira com `echo $$` não — compare o PID antes/depois num wrapper).
2. **Modifique**: troque o alvo para `env` (lista o ambiente) e depois `sh -c` não — use `echo` com um argumento.
3. **Aplique**: escreva um wrapper `meu-ls` que loga "rodando ls" e então `syscall.Exec` o `ls` real, passando `os.Args[1:]` como argumentos.
