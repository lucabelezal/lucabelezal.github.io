Um array tem tamanho fixo; quase nenhuma lista real é. O **slice** é a resposta de Go: uma visão **dinâmica** sobre um array — cresce, encolhe, fatia — e é o tipo que você usará para a maioria esmagadora das coleções. Entender slice é entender três números: o **ponteiro** para o array, o `len` (quantos elementos você enxerga) e o `cap` (até onde o array vai). Metade dos bugs de quem está começando em Go mora aqui — vale a pena dominar.

## Slice por dentro: ponteiro + len + cap

Um slice é um **header** de três campos: um ponteiro para o primeiro elemento do array interno, o `len` (elementos visíveis) e o `cap` (capacidade até o fim do array). É por isso que ele é barato de copiar — copiar o header não copia os dados.

A consequência mais importante: **fatiar não copia dados**. `l := s[2:5]` cria outro header apontando para o **mesmo array**:

Isso não é bug — é o *design*. Fatiar é O(1). Mas você precisa saber quando **compartilhar é o que quer** (ler um pedaço sem copiar) e quando precisa de uma **cópia** (`copy` ou `slices.Clone`).

## `append` e a realocação

`append` tem duas vidas: se há espaço no array (`cap` sobrando), escreve no mesmo array — o slice antigo vê a mudança; se não há, aloca um **array novo, maior**, copia tudo e devolve um slice novo. Como você nunca sabe qual dos dois aconteceu, a regra é sagrada: **`s = append(s, x)`** — sempre capture o retorno.

O bug clássico:

```go
a := []int{1, 2, 3, 4, 5}
b := a[:2]        // len 2, mas cap alcança o fim do array de a (posições 2..4 livres)
b = append(b, 99) // cabe no array de a! escreve em a[2]
fmt.Println(a)    // [1 2 99 4 5] — a foi alterado por "baixo dos panos"
```

`b` tinha `cap` sobrando, então o `append` não realocou — e sobrescreveu o vizinho de `a`. Se você não quer esse efeito, use `b = append(slices.Clone(a[:2]), 99)` ou reserve capacidade extra de propósito.

## `nil` × slice vazio

`var s []string` é `nil` (len 0). `make([]string, 0)` **não** é `nil` (é um slice vazio com array por baixo). Os dois se comportam igual em `len`, `append` e `range` — mas **diferem na serialização**: em JSON, `nil` vira `null` e o vazio vira `[]`. Para APIs, prefira `make([]T, 0)` quando o campo representa "lista que pode ser vazia".

## Slice já é uma referência — não passe `*[]int`

Retomando a página de [Ponteiros](pointers): slices já carregam um ponteiro interno. Uma função que recebe `[]int` e faz `s[i] = x` **altera o array compartilhado** — sem ponteiro. O único caso que exige retorno é o `append` (realocação). Por isso a assinatura idiomática é `func f(s []int) []int`, **nunca** `func f(s *[]int)` — exceção rara para funções que precisam trocar o slice inteiro (como o `sort.Slice` interno).

## Armadilhas comuns

- **Esquecer o retorno do `append`**: `append(s, x)` sem `s =` não tem efeito quando realoca — e o bug só aparece de vez em quando (quando não realoca). Capture sempre.
- **`append` num slice fatiado**: sobrescreve o vizinho no array compartilhado (exemplo acima). Conheça o `cap` ou clone.
- **Indexar fora do `len`**: `s[5]` com len 3 é *panic*. Fatie ou faça `append` em vez de escrever em índice inexistente.
- **Comparar com `==`**: slices não são comparáveis (exceto com `nil`). Use `slices.Equal`.
- **`copy` com destino pequeno**: `copy` copia no máximo `len(destino)` — um destino menor que a fonte copia truncado, sem erro. Confira tamanhos.
- **`range` copia o elemento**: `for _, v := range s` dá a **cópia** de cada elemento; `v = ...` não altera o slice. Para mutar, use o índice.
