Quando uma função precisa **mudar** um valor que vive fora dela, um valor copiado não serve — a função precisa saber *onde* o dado está. Pense num banco: para mostrar ao cliente uma simulação de saldo, você pode trabalhar com uma cópia; mas para registrar um depósito, a função precisa acessar o saldo **real**, não uma cópia. O *ponteiro* resolve isso: em vez de enviar o dado, você envia o **endereço** dele na memória. É o assunto que mais confunde quem vem de Python, Java ou JavaScript — e, em Go, é mais simples e seguro do que parece.

## Go é sempre passagem por valor — o ponteiro muda isso

Go **sempre** copia os argumentos ao chamar uma função. A pergunta não é "passo por valor ou por referência?", e sim: **o que estou copiando?**

- Se copio um `int`, mudo a cópia — o original não muda.
- Se copio um **ponteiro** (que é só um endereço), a função ganha uma cópia do endereço — e através dele alcança e altera o dado original.

Os dois operadores são as duas faces da mesma moeda: `&x` **pega o endereço** de `x`; `*p` **segue o endereço** para ler ou escrever o valor que está lá. O tipo `*int` se lê "ponteiro para `int`". O *zero value* de qualquer ponteiro é `nil` — aponta para lugar nenhum.

O exemplo clássico é a troca de valores:

## Quando usar ponteiro (e quando não)

O instinto saudável em Go é o **oposto** do de C: comece sem ponteiro e adicione só quando existe um motivo real. Use ponteiro quando:

- **Precisa mutar o original** — o caso do `troca` e de setters.
- O **struct é grande** e copiar dezenas de campos a cada chamada é caro (dezenas de bytes → fica na stack, cópia barata; structs com slices, maps e strings por dentro são só headers — copiar o header não copia o conteúdo).
- Quer expressar **ausência**: um campo `*string` pode ser `nil` ("não informado"), enquanto `""` é ambíguo entre vazio e ausente.
- O método **muta o receiver** (página de [Métodos](methods)).

Não use quando:

- O tipo **já carrega referência interna**: `slice`, `map`, `channel`, função e interface. Slices e maps já apontam para os dados; você não precisa de `*[]int`. Cuidado com a exceção do `append`, que pode realocar e devolver outro slice — por isso a assinatura idiomática é `func f(s []int) []int`, **devolvendo** o slice, não recebendo `*[]int` (detalhe na página de [Slices](slices)).
- Só vai **ler** o valor — receba por valor: fica explícito que não há efeito colateral.
- Quer "otimizar" sem medir. Ponteiro às vezes **piora**: se o compilador vê que o ponteiro escapa da função, aloca no *heap* e gera trabalho para o coletor de lixo; uma struct pequena por valor fica na stack, sem GC.

## `nil`: o ponteiro que não aponta para nada

Dereferenciar um ponteiro `nil` derruba o programa em runtime:

```go
var u *Usuario // nil
fmt.Println(u.Nome) // panic: runtime error: invalid memory address or nil pointer dereference
```

Quando o ponteiro pode vir `nil` (de uma busca, de um JSON, de uma função que "talvez" retorne), cheque antes de usar:

```go
if u != nil {
    fmt.Println(u.Nome)
}
```

Esse *panic* e a arte de tratá-lo são explorados em [Panic](panic) e [Erros](errors).

## `new(T)`, `&T{}` e retornar endereço local

Duas formas de obter um ponteiro:

```go
p := new(int)             // *int apontando para um int zerado
u := &Usuario{Nome: "Ana"} // *Usuario, já inicializado — o idiomático
```

`new(T)` é raro em código real; `&T{...}` domina. E, diferente de C, **retornar o endereço de uma variável local é seguro**: o compilador percebe (via *escape analysis*) que o valor escapa da função e o move para o heap, onde o coletor de lixo cuida do ciclo de vida. É exatamente o que o `newPerson` de [Structs](structs) faz.

## Ponteiros e concorrência: o aviso

Compartilhar um ponteiro mutável entre **goroutines** sem sincronização é *data race*: comportamento indefinido que só aparece sob carga. A regra do Go é "não compartilhe memória comunicando; comunique compartilhando memória" — detalhe que você vai enfrentar no bloco de [Goroutines](goroutines).

## Armadilhas comuns

- **Dereferenciar `nil`**: qualquer acesso a `*p` com `p == nil` é panic. Cheque antes quando o ponteiro vem de fora.
- **Salvar o endereço da variável de um `for` (Go antigo)**: em versões anteriores à 1.22, `for _, v := range xs { save(&v) }` guardava o mesmo endereço a cada iteração. Desde o Go 1.22 a variável é nova por iteração — mas código legado pode ter o bug.
- **Cadeia com `nil` no meio**: `a.b.c` pânica se `a.b` for `nil`. Inicialize a cadeia ou valide por partes.
- **Achar que `x := y` (com ponteiros) cria um objeto novo**: `y` continua sendo o mesmo dado; `x` só ganha outro nome para o mesmo endereço.

## Pratique

1. **Reproduza**: rode `pointers.go` e `troca.go`; explique, linha a linha, por que um zera e o outro não.
2. **Modifique**: escreva `func dobro(n *int)` que dobra o valor apontado (`*n = *n * 2`) e chame com `&x`. Depois faça a mesma coisa recebendo `int` por valor e compare.
3. **Aplique**: escreva `func paraMaiusculas(s *string)` que converte a string apontada com `strings.ToUpper` — e trate o caso em que o ponteiro é `nil` antes de dereferenciar.
