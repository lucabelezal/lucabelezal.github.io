A maioria das falhas em Go é **valor** (`error`) e segue o fluxo normal. Mas existe um tipo de falha que não devolve erro nenhum — porque **o programa não deveria continuar**: uma invariante quebrada, um bug, um "isto não pode acontecer". Para esses casos Go tem o **`panic`**: derruba a goroutine atual, desempilhando chamadas, e termina o programa se ninguém recuperar.

## Quando panic é a resposta certa — e é raro

A regra do Go: **erro esperado é `error`; situação impossível é `panic`**. Usos legítimos:

- **Invariante quebrada**: o código chegou num estado que "não pode" existir (ex.: `switch` sem `default` num enum que deveria ser exaustivo).
- **Erro de programação**: indexar fora do slice, dereferenciar `nil`, `assert` de premissa. (Aliás: esses *já* panican sozinhos no Go — `index out of range`, `nil pointer dereference` — sem você chamar `panic`.)
- **Setup que não pode falhar**: um programa que sem configuração não tem o que fazer.
- **`main`**: se o programa não consegue nem começar, panic é aceitável — a mensagem + trace vai para o log e o exit code é não-zero.

O que **não** é motivo: erro de entrada, de usuário, de I/O esperado, parsing que pode falhar. Tudo isso retorna `error`. Se você tem um `panic` no caminho feliz do seu programa, é provável que devesse ser um erro.

## Não há try/catch — e isso é de propósito

`panic` não é um mecanismo genérico de erro estilo exceção. Quando um panic não é recuperado, o programa **morre** — sem "catch-all" escondido. Essa escolha força o código a tratar falha como valor e a reservar `panic` para o que é genuinamente inesperado. O `defer` roda durante um panic (antes do programa morrer) — e o [Recover](recover) é a única forma de interceptá-lo, e só na própria goroutine.

Dois detalhes que mordem:

- **Panic numa goroutine derruba o programa inteiro** — não só a goroutine. Um worker que panica leva o processo junto, a menos que a goroutine tenha um `recover` (página de [Goroutines](goroutines) e [Recover](recover)).
- **`panic` ≠ `os.Exit`**: antes de morrer, o panic roda os `defer`s (úteis para logging/cleanup) e imprime o trace; `os.Exit` termina na hora, sem rodar nada (detalhe em [Exit](exit)).

## Em código real

Panics aparecem em bibliotecas para *premissas de uso*: chamar um método sem inicializar, um tipo inválido numa conversão irrecuperável. Mas a boa biblioteca **documenta** que aquilo é um panic e devolve `error` para tudo que o chamador pode evitar. Frameworks HTTP (como o `net/http`) colocam um `recover` na fronteira de cada request para um handler com bug não derrubar o servidor — você verá o padrão em [Servidor HTTP](http-server).

## Armadilhas comuns

- **Panic para erro de entrada**: validar usuário com `panic` derruba o servidor. Retorne `error`.
- **Achar que panic é local**: sem recover, ele derruba a **goroutine inteira** — e se for a `main`, o programa.
- **Recuperar na goroutine errada**: `recover` só funciona na goroutine que panica (e dentro de um `defer`). Tentar recuperar de fora não adianta.
- **Mensagem vazia**: `panic("")` não diz nada no log. Inclua o contexto: `panic(fmt.Sprintf("estado inválido: %v", s))`.

## Pratique

1. **Reproduza**: rode `panic.go` e leia o trace — identifique a linha que panica e o exit status.
2. **Modifique**: comente o primeiro `panic` e deixe o segundo rodar; force o erro criando em um caminho inválido (ex.: um diretório que não existe). Observe a mensagem do `os.Create` envolvida no panic.
3. **Aplique**: numa função de conversão, troque um `panic` que você escreveria por retorno `(T, error)` — e decida em qual caso um `panic` seria genuinamente justificável.
