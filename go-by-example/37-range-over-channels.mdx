A página anterior consumiu um canal com `v, ok := <-ch` num laço manual. Quando a intenção é só "pegue **todos** os valores até fechar", o **`range`** faz isso numa linha: ele recebe cada valor e termina sozinho quando o canal é fechado.

## A regra implícita: quem não fecha, o range não termina

`range` sobre um canal só termina quando o canal é **fechado**. Um canal aberto (mesmo sem valores) deixa o `range` **bloqueado esperando** — como qualquer receive. Por isso o produtor precisa `close` quando terminar; senão, quem itera fica preso (deadlock se for o fim do programa).

## O padrão consumidor

```go
for job := range jobs {   // recebe até o produtor fechar
    processar(job)
}
```

É o consumidor de fila mais comum em Go — você já viu em [Worker Pools](worker-pools) e no [Ciclo de Vida](goroutine-lifecycle): produtor envia e fecha; consumidor `range` até o fim.

## Em código real

- **Filas de trabalho**: cada worker `range` no canal de jobs.
- **Streams**: uma goroutine produtora (leitura de arquivo, eventos) envia e fecha ao acabar; o consumidor processa com `range`.
- **Não precisa fechar canais de um único uso** se não há `range`/fim esperado — feche para **sinalizar o fim** a quem itera.

## Armadilhas comuns

- **`range` sem `close`**: o laço nunca termina. Garanta o fechamento (e quem fecha é o produtor).
- **`range` com canal que nunca recebe**: bloqueia esperando o primeiro valor — normal, mas confirme que o produtor existe.
- **Fechar para "limpar"**: se o consumidor não usa `range`/`ok`, o close é desnecessário (e perigoso se ainda houver envios).
- **`range` de um canal que outros ainda enviam**: o laço só para no close; produtores paralelos precisam parar de enviar **antes** do close para não dar panic.

## Pratique

1. **Reproduza**: rode `range-over-channels.go`; remova o `close` e observe o deadlock.
2. **Modifique**: itere um canal que recebe de uma goroutine produtora (que envia 5 números e fecha) — processe e some.
3. **Aplique**: monte o pipeline produtor→worker com `range` no worker e um `WaitGroup` esperando os workers terminarem de drenar.
