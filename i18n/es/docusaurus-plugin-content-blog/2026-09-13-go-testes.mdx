## 1. Contexto

`go test` corre archivos `*_test.go`, con caché por defecto y `-count=1` para forzar. Convención: funciones `TestXxx(t *testing.T)`, `t.Fatalf` para fallar con mensaje, `t.Run` para subtests. Tabla = slice de structs `{name, in, want}`: añadir casos es añadir filas, sin funciones nuevas.

## 2. El problema

El test de "ejemplo único" se pudre: cubre el camino feliz, esconde bordes (vacío, nil, cero), y cuando rompe nadie sabe qué caso. Peor: concurrencia sin `-race` pasa verde con race escondida — el detector existe justo porque el ojo humano no atrapa intercalaciones.

## 3. Modelo mental

**El caso es dato, no código.** La tabla separa *qué* (filas) del *cómo* (runner). Los nombres de caso se vuelven documentación ejecutable (`TestSum/vazio`).

**`-race` instrumenta, no adivina.** Rastrea accesos entre goroutines en runtime; cuesta ~10x — por eso vive en CI, no en producción.

**Prueba comportamiento observable.** Logs (campos, redaction), conteo de goroutines, salidas — no internos. Refactorizar sin romper tests prueba que apuntan al contrato.

![Diagrama: tabla de casos alimentando subtests, -race por encima](/img/diagramas/go-testes-tabela.svg)

**Regla práctica.** Bug nuevo → caso nuevo en la tabla primero (reproduce), después el fix. La tabla crece con los incidentes.

## 4. Implementación

```go title="sum_test.go" showLineNumbers
func TestSum(t *testing.T) {
	tests := []struct {
		name string
		in   []int
		want int
	}{
		{"vazio", nil, 0},
		{"um", []int{5}, 5},
		{"varios", []int{1, 2, 3}, 6},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			if got := Sum(tt.in); got != tt.want {
				t.Fatalf("Sum(%v) = %d, want %d", tt.in, got, tt.want)
			}
		})
	}
}
```

Comando completo del CI: `go test -race -count=1 ./...` — sin caché, con detector, en todo. Para logs: handlers en `bytes.Buffer` + `json.Unmarshal` afirmando `order_id` y `[REDACTED]` (patrón del post de errores). Para leaks: `runtime.NumGoroutine()` antes/después del escenario (patrón del post de concurrencia: 1 → 1).

## 5. Fallas y trade-offs

**Probar implementación.** Afirmar llamadas internas u orden de locks rompe en cada refactor honesto. Apunta a salidas y efectos.

**`time.Sleep` para sincronizar tests.** Flaky por construcción: rompe en CI lento, desperdicia en CI rápido. Sincroniza con channels/`Wait`/contextos con timeout — nunca con apuestas.

**Cobertura como meta.** 100% con asserts vacíos miente mejor que 70% honesto. La cobertura guía dónde faltan casos; no prueba nada sola.

**Probar terceros.** Mockear bibliotecas para afirmar su comportamiento prueba el mock. Prueba tu integración (el contrato que usas), no la lib.
