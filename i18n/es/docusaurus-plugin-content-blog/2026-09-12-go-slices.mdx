## 1. Contexto

Los arrays en Go son valores de tamaño fijo — y el tamaño es parte del tipo (`[4]int` ≠ `[5]int`). Asignar copia todo. Para listas que crecen, el lenguaje ofrece el slice: una vista flexible sobre un array, que crece por `append`.

La definición que importa, directo del runtime (`runtime/slice.go`):

```go title="runtime/slice.go"
type slice struct {
	array unsafe.Pointer
	len   int
	cap   int
}
```

Tres palabras. El `array` apunta al primer elemento del backing array; `len` cuenta los elementos visibles; `cap` cuenta hasta dónde se puede ir sin realocar:

![Diagrama: header ptr/len/cap apuntando al backing array](/img/diagramas/go-slices-header.svg)

Andrew Gerrand resume la consecuencia: rebanar no copia datos — crea un nuevo descriptor sobre el mismo array, lo que hace las operaciones tan baratas como manipular índices ([Go Slices: usage and internals](https://go.dev/blog/slices-intro)). Barato, pero compartido: ahí viven los bugs.

> **Definición (propuesta).** Slice es un valor de tres palabras (puntero, tamaño, capacidad) que describe un segmento de array. Copiar el descriptor es barato; los elementos siguen compartidos hasta realocar.

## 2. El problema

Rebanas un array y ajustas un elemento del slice:

```go title="main.go" showLineNumbers
a := [6]int{12, 43, 55, 35, 1, 99}
t := a[1:4]
t[0] = 77
fmt.Println("shared:", t, "| array:", a)
```

```bash title="Terminal"
shared: [77 55 35] | array: [12 77 55 35 1 99]
```

`a[1]` pasó a 77 sin que nadie tocara `a`. El slice y el array dividen la memoria — escribir por el slice escribe en el array. La peor versión (capítulo "Tricky Slices", Boot.dev): dos `append`s de la misma base con capacidad sobrante se sobrescriben en silencio, porque ninguno realocó. El problema nunca es el `append` en sí — es el **compartir invisible** del backing array.

## 3. Modelo mental

**Rebanar comparte; copiar separa.** `t := a[1:4]` crea descriptor nuevo (ptr a `a[1]`, len 3, cap 5 — la capacidad cuenta desde el inicio del slice hasta el fin del array). `copy(dst, src)` o `slices.Clone` crean array nuevo. Decide por intención: ventana sobre datos vivos → rebana; valor independiente → clona.

**`len` manda; `cap` sugiere.** Solo índices `< len` son accesibles — `s[3]` con len 3 causa panic aun con cap 5. `cap` existe para que `append` sepa cuándo realocar, y para que prealoques con `make([]int, 0, 1000)`.

**Nil vs vacío: puntero nil vs array asignado.** `var s []int` tiene `array == nil` (es nil); `[]int{}` y `make([]int, 0)` apuntan a array de tamaño cero (vacíos, no nil). Misma distinción del Post 1, una capa arriba — y con reflejo en JSON: el slice nil serializa `null`, el vacío `[]`.

**Append devuelve descriptor nuevo — usa el retorno.** `append` puede realocar (nuevo array, nuevo ptr) o no (mismo array, len mayor). En ambos casos el descriptor correcto está en el retorno. `s = append(s, x)` siempre; `append(s, x)` suelto descarta justo lo que cambió.

**Regla práctica.** El slice no es "tipo por referencia" — es valor de tres palabras con puntero dentro. Toda sorpresa desaparece cuando dibujas el header antes de predecir el comportamiento.

## 4. Implementación

### Crecimiento real (Go 1.26, salidas reales)

```go title="main.go" showLineNumbers
var s []int
for i := 0; i < 10; i++ {
	s = append(s, i)
	fmt.Println("len:", len(s), "cap:", cap(s))
}
```

```bash title="Terminal"
len: 1 cap: 4
len: 2 cap: 4
len: 3 cap: 4
len: 4 cap: 4
len: 5 cap: 8
len: 6 cap: 8
len: 7 cap: 8
len: 8 cap: 8
len: 9 cap: 16
len: 10 cap: 16
```

Nota el primer salto: 0 → 4, no 0 → 1. El compilador actual asigna un backing especulativo en **stack** antes del loop ([Randall, Allocating on the Stack](https://go.dev/blog/allocation-optimizations)) — tutoriales viejos que muestran 1, 2, 4 describen otro compilador. La fórmula exacta vive en `nextslicecap` del runtime: ~2x en slices pequeños, suavizando hacia ~1,25x en grandes, siempre redondeada a clases de tamaño.

![Diagrama: len lleno dispara nuevo array mayor; descriptor actualizado](/img/diagramas/go-slices-append-es.svg)

### Separando lo compartido: `Clone` y `Clip`

```go title="main.go" showLineNumbers
u := slices.Clone(t)
u[0] = 43
fmt.Println("cloned:", u, "| orig:", t)

full := []int{1, 2, 3, 4, 5}
w := full[:2]
fmt.Println("clipped:", slices.Clip(w), len(w), cap(slices.Clip(w)))
```

```bash title="Terminal"
cloned: [43 55 35] | orig: [77 55 35]
clipped: [1 2] 2 2
```

`Clone` copia elementos a array nuevo (el original respira); `Clip` quita la capacidad no usada (`s[:len(s):len(s)]`), bloqueando el slice contra appends ajenos que escribirían en tu array. El paquete [`slices`](https://pkg.go.dev/slices) (stdlib) jubila buena parte del `copy`/`append` manual: `Grow`, `Concat`, `Compact`, `Delete`.

**Regla práctica.** Función que recibe slice y guarda: clona a la entrada o documenta el compartir. El slice que cruza fronteras de API sin dueño claro se vuelve aliasing a distancia.

## 5. Fallas y trade-offs

**"Append duplica la capacidad".** Falso en general: duplica en pequeño, ~1,25x en grande, clases de tamaño en medio — y Go 1.26 aún anticipa stack. Quien dimensiona protocolos o formatos binarios contando con "duplica" se equivoca. Fuente: el runtime, no tutoriales.

**Append en base compartida.** Dos slices del mismo array con cap sobrante: el append en uno escribe "dentro" del otro. Defensa canónica: full slice expression `s[1:3:3]` limita el cap del rebanado, forzando realocar al primer append — aislamiento por construcción.

**Nil vs vacío en JSON.** `var s []int` → `null`; `[]int{}` → `[]`. APIs que prometen listas y entregan `null` rompen clientes tipados. Decide por contrato: `make`/`Clone` (nunca nil) cuando la respuesta debe ser lista.

**"Tipo por referencia".** La formulación que este post jubila: el slice se pasa por valor como todo en Go — el header se copia en cada llamada (por eso `append` sin usar el retorno "no pega", igual que el `increment` del Post 1). Llamarlo referencia esconde justo el mecanismo que explica los bugs.
