Una API HTTP en Go necesita cuatro cosas: escuchar en un puerto, rutear paths a funciones, leer/escribir JSON y loguear con identidad. La stdlib entrega las cuatro desde Go 1.22 — sin framework. Construyamos en ese orden, una capa a la vez, cada una corriendo antes de la próxima.

Post independiente, validado con `curl` real. Salidas reales, Go 1.26.

## 1. Contexto

Los frameworks resuelven lo que la stdlib ya resuelve desde 1.22: rutear por método y patrón, servir con timeouts, apagado con drenaje. Empieza stdlib: menos capas para depurar, upgrades sin breaking. Los frameworks entran cuando duela de verdad (validación compleja, OpenAPI generado) — no antes.

![Diagrama: request cruza middleware, handler, JSON de vuelta](/img/diagramas/go-http-cadeia.svg)

## 2. El problema

APIs sin request_id: tres requests fallan juntos y el log no dice cuál es cuál. Sin timeouts: handlers lentos retienen conexiones para siempre. Sin Content-Type: los clientes adivinan cuerpos. Cada uno ya tumbó producción real — y ninguno necesita framework.

## 3. Paso 1 — el menor servidor que responde

```go title="main.go" showLineNumbers
package main

import "net/http"

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
		w.Write([]byte("ok"))
	})
	http.ListenAndServe("127.0.0.1:18098", mux)
}
```

Tres piezas, nada más:

- **`http.NewServeMux()`** — el router: tabla de path → función.
- **`HandleFunc("GET /health", func...)`** — registra ruta. El `"GET "` inicial (Go 1.22+) separa por método: mismo path, distintos métodos, distintas funciones.
- **La función handler** — siempre `func(w http.ResponseWriter, r *http.Request)`: `w` es por donde sale la respuesta, `r` es lo que llegó.

```bash title="Terminal"
$ curl http://127.0.0.1:18098/health
ok
```

Servidor en el aire. Todo lo demás de este post son capas sobre estas 10 líneas.

## 4. Paso 2 — JSON de verdad

Texto plano no es API. Cambiamos la respuesta por JSON y añadimos una ruta POST que lee JSON:

```go title="main.go" showLineNumbers
mux.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(map[string]string{"status": "ok"})
})
mux.HandleFunc("POST /double", func(w http.ResponseWriter, r *http.Request) {
	var in struct{ N int `json:"n"` }
	if err := json.NewDecoder(r.Body).Decode(&in); err != nil {
		http.Error(w, "json inválido", http.StatusBadRequest)
		return
	}
	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(map[string]int{"result": in.N * 2})
})
```

Dos reglas que evitan bugs clásicos:

1. **Content-Type antes del primer `Encode`.** Tras el primer byte, el header traba — clientes sin Content-Type adivinan cuerpos (y proxies reescriben).
2. **JSON inválido = 400 honesto**, no 500. 400 dice "tu request está mal"; 500 dice "yo me rompí". Mezclarlos corrompe alertas y dashboards.

```bash title="Terminal"
$ curl http://127.0.0.1:18098/health
{"status":"ok"}
$ curl -X POST http://127.0.0.1:18098/double -d '{"n":21}'
{"result":42}
$ curl -X POST http://127.0.0.1:18098/double -d 'xxx'
json inválido
```

## 5. Paso 3 — middleware: qué request es cuál

Con dos rutas, los logs ya se mezclan. El middleware lo resuelve: una función envolviendo el router, sellando `request_id` y midiendo duración:

```go title="main.go" showLineNumbers
func mw(log *slog.Logger, next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		id := fmt.Sprintf("req-%d", time.Now().UnixNano()%100000)
		ctx := context.WithValue(r.Context(), reqKey, id)
		l := log.With(slog.String("request_id", id))
		start := time.Now()
		next.ServeHTTP(w, r.WithContext(ctx))
		l.Info("done", slog.String("method", r.Method), slog.String("path", r.URL.Path), slog.Duration("ms", time.Since(start)))
	})
}
```

Lee de dentro hacia fuera: genera `id`, lo cuelga del `ctx` (los handlers abajo lo leen sin parámetro extra), deriva logger con el id, anota el reloj, **llama la próxima capa**, loguea método + path + duración. Middleware es cebolla: request_id primero (todo abajo loguea con él), recovery por fuera de todo.

```bash title="Terminal"
{"level":"INFO","msg":"done","request_id":"req-69000","method":"GET","path":"/health",...}
{"level":"INFO","msg":"done","request_id":"req-20000","method":"POST","path":"/double",...}
```

Tres requests, tres identidades — el log ahora responde "cuál falló".

## 6. Fallas y trade-offs

**Framework el día uno.** Chi/Gin/Fiber antes del primer dolor: capas para depurar, upgrades con breaking, lock-in de convención. Adopta cuando la stdlib pruebe límites.

**Sin timeouts en el servidor.** Handlers con `ctx` no salvan conexiones sin `ReadTimeout`/`WriteTimeout` en `http.Server`: Slowloris ocupa workers gratis. Timeouts en ambas puntas + shutdown gracioso (el `main` real del post de concurrencia).

**`request_id` generado en handlers.** Muy tarde: middlewares anteriores ya loguearon sin él. Genera en el borde (primer middleware), propaga vía `ctx`.
