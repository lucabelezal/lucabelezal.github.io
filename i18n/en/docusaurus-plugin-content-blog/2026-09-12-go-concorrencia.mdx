## 1. Context

A process is a running program (isolated memory). A thread is the OS's execution unit (sharing the process memory). A **goroutine** is the Go runtime's unit: ~2KB starting stack, born with a `go`, multiplexed by the scheduler onto real threads (M:N model). Spawning 100k goroutines is routine; 100k threads is suicide.

Concurrency = managing many independently-progressing tasks (interleaving on one core). Parallelism = literally executing at once (several cores). Always concurrent Go; parallel when the scheduler has free cores:

![Diagram: interleaving on one core vs simultaneous execution on two cores](/img/diagramas/go-conc-vs-par-en.svg)

Go's motto, inverted on purpose: **don't communicate by sharing memory; share memory by communicating** — channels carry values (often copies) instead of exposing mutable state.

### Analogy: the kitchen

A restaurant kitchen separates both concepts cleanly. Three orders arrive — burger, pasta, dessert:

**Concurrency: one cook, three orders.** They alternate: meat on the grill, pasta while it cooks; back to the burger, ahead on dessert. Progress-wise everything moves together — but physically one thing at a time.

**Parallelism: three cooks.** One per order, literally simultaneous execution.

And the case that matters for Go:

```text
1 cook + 3 orders → CONCURRENCY
3 cooks + 3 orders → CONCURRENCY + PARALLELISM
```

Concurrency and parallelism aren't opposites — a system can be both. The Go mapping:

```text
Orders → goroutines (go processOrder(orderA))
Cook → OS thread
Head chef → runtime scheduler (GOMAXPROCS)
```

`go` before a call promises no three CPUs — it promises three managed tasks. With free cooks (cores), the scheduler truly parallelizes.

![Diagram: 1 cook alternating orders vs 3 cooks in parallel, mapped to Go](/img/diagramas/go-conc-cozinha-en.svg)

## 2. The problem

One hundred goroutines incrementing a counter. It runs, prints 100, looks right:

```go title="main.go" showLineNumbers
var total int
var wg sync.WaitGroup
for i := 0; i < 100; i++ {
	wg.Add(1)
	go func() {
		defer wg.Done()
		total++
	}()
}
wg.Wait()
fmt.Println("sem mutex:", total)
```

```bash title="Terminal"
sem mutex: 100
```

100 by luck. With `-race`, the truth:

```bash title="Terminal"
WARNING: DATA RACE
Previous write at ... by goroutine 7:
    main.go:15
```

`total++` isn't atomic (read, add, write) — two goroutines interleave and one update is lost. Without the detector, the bug surfaces in production, at 3am, once a month. With it, it surfaces in CI today.

## 3. Mental model

**Unbuffered channels are handshakes; buffered ones are queues.** `ch := make(chan int)` completes a send only when someone receives (rendezvous — synchronizes). `make(chan int, 3)` queues up to 3 without blocking (decouples pace). Closing (`close`) signals the end to `range`; sending on closed panics.

**`WaitGroup`: whoever `Add`s doesn't `Done`.** `Done` belongs to the worker goroutine (via `defer`, first line). A common wrong pattern — even in good teaching material — is `main` calling `Done` while consuming the channel: it works by accident when items == Adds, and explodes into `negative WaitGroup counter` at the first divergence. Work owner, `Done` owner.

**Mutexes vs channels: guard data with mutexes, coordinate flow with channels.** Shared counters → `sync.Mutex`. Orchestration (work done, stage end, parallelism caps) → channels. "Mutexes for everything" serializes the whole program; "channels for everything" spreads state across an invisible protocol.

**Rule of thumb.** Shared mutable data: mutexes plus `-race` in CI. Flow between stages: channels. Never both for the same problem.

### Inside channels: `hchan` in 30 seconds

Every `make(chan T, N)` creates a heap `hchan`: ring buffer (`buf`, `sendx`, `recvx`, `qcount`), `closed` flag, internal lock, and two queues — `sendq` and `recvq` — of parked goroutines (`sudog` records: which goroutine, which value, which channel). Three optimizations explaining behavior:

- **Direct stack→stack copy.** With a waiting receiver and no buffer, the runtime copies from the sender's frame to the receiver's frame — no heap in between. Unbuffered channels can beat buffered ones under low contention.
- **Close wakes everyone.** `close` sets the flag and unparks: receivers drain the buffer then get zero values; parked senders panic. Closing twice: panic.
- **Happens-before rules** (memory model): sends happen-before matching receives; `close` happens-before receives returning zero because of it. Write side effects **before** the send/close — after it, nothing is guaranteed.

For the full dive (send/receive lifecycle, `select` internals, sudog recycling): [Gabor Koos, Go Channels Internals](https://blog.gaborkoos.com/). Executable pattern catalog: [symonk/go-concurrency-deep-dive](https://github.com/symonk/go-concurrency-deep-dive).

### GMP: who runs your goroutine

Under `go f()` sits the scheduler with three letters: **G** (goroutine), **M** (OS thread), **P** (processor — execution context, `GOMAXPROCS` = core count by default). Goroutines enter queues (one global + one local per P); idle Ps **steal** work from others' queues (work stealing):

![Diagram: GMP scheduler with work stealing](/img/diagramas/go-conc-gmp-en.svg)

Observable live with `GODEBUG=schedtrace=1000` (real output, `GOMAXPROCS=2`):

```bash title="Terminal"
SCHED 0ms: gomaxprocs=2 idleprocs=0 threads=4 runqueue=0 [ 1 0 ]
```

`runqueue=0` = empty global queue; `[ 1 0 ]` = one goroutine in P0's local queue, zero in P1's. When P1 drains, it steals from P0 instead of sleeping — that's how 100k goroutines live on a few threads.

Three scheduler details worth the model: **async preemption** (since Go 1.14, ~10ms via SIGURG — endless loops without calls no longer stall the scheduler); **netpoller** (I/O becomes epoll/kqueue events: goroutines sleep without holding P); **blocking syscalls release P** (another thread takes over while one waits on the kernel). Scalable concurrency is born from these three.

### `select`: one listener, several channels

When one goroutine serves several channels, `select` fires the first ready one (ties: random draw):

```go title="main.go" showLineNumbers
chInts := make(chan int, 1)
chStrs := make(chan string)
chInts <- 42

select {
case i := <-chInts:
	fmt.Println("int:", i)
case s := <-chStrs:
	fmt.Println("str:", s)
default:
	fmt.Println("nothing ready")
}
```

```bash title="Terminal"
int: 42
```

Without `default`, `select` blocks until some case frees up — with `default`, it becomes a non-blocking check ("anything? otherwise, moving on"). Dataless signals use `chan struct{}`: zero bytes, communicating only the instant.

### Nil vs closed: the matrix

| | send | receive |
|---|---|---|
| nil (uncreated) | blocks forever | blocks forever |
| open | blocks if full (or rendezvous) | blocks if empty |
| closed | **panic** | zero value + `ok=false` (after draining the buffer) |

```go title="main.go"
close(chInts)
v, ok := <-chInts
fmt.Println("closed:", v, ok)
```

```bash title="Terminal"
closed: 0 false
```

Two precision notes: channels, like slices and maps, are **values with an internal pointer** — copying shares the queue (not "reference types" in the pass-by-reference sense; everything in Go passes by value, Post 1). And closing is optional for the GC: close to signal the end to the receiver (`range` terminates), never to "free memory".

## 4. Implementation

### Mutex: same program, no race

```go title="main.go" showLineNumbers
var total int
var mu sync.Mutex
var wg sync.WaitGroup
for i := 0; i < 100; i++ {
	wg.Add(1)
	go func() {
		defer wg.Done()
		mu.Lock()
		total++
		mu.Unlock()
	}()
}
wg.Wait()
fmt.Println("com mutex:", total)
```

```bash title="Terminal"
com mutex: 100
```

`go run -race`: silence — RACE-CLEAN. The lock serializes only the critical line (nanoseconds); everything else stays parallel.

### `RWMutex`: simultaneous reads, exclusive writes

When reads dominate, `sync.Mutex` wastes: readers could run together. `RWMutex` splits — many simultaneous `RLock`s, exclusive `Lock`:

```go title="main.go" showLineNumbers
var mu sync.RWMutex
users := map[string]int{"ada": 36}

go func() {
	mu.RLock()
	_ = users["ada"]
	mu.RUnlock()
}()

mu.Lock()
users["bob"] = 30
mu.Unlock()
```

Convention: the variable is called `mu`, and `Unlock` goes `defer`red right after `Lock` — forgetting to unlock is self-inflicted deadlock. Maps, reminder: pure concurrent reads are safe; the danger is reading alongside writing (the runtime kills with `fatal error: concurrent map read and map write`).

### Structs with mutexes: the Counter pattern

Real cases are rarely bare `int`s — they're state inside structs. The mutex lives with the data it guards, and methods are the only door (straight bridge to the packages post's visibility: lowercase field, uppercase method):

```go title="main.go" showLineNumbers
type Contador struct {
	mu    sync.Mutex
	valor int
}

func (c *Contador) Incrementar() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.valor++
}

func (c *Contador) Valor() int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return c.valor
}
```

**Pointer** receivers required: value receivers would copy the mutex each call (Post 2's `go vet` flags it). `Contador{}` comes out usable — useful zero value, no constructor.

### Worker pool: semaphores with buffered channels

```go title="main.go" showLineNumbers
jobs := make(chan int, 3) // semaphore: 3 slots
var wg2 sync.WaitGroup
for w := 0; w < 3; w++ {
	wg2.Add(1)
	go func(id int) {
		defer wg2.Done()
		for j := range jobs {
			_ = j // process
		}
	}(w)
}
for i := 0; i < 9; i++ {
	jobs <- i
}
close(jobs)
wg2.Wait()
```

```bash title="Terminal"
pool processou: 9
```

Nine jobs, three workers: the buffer caps parallelism with no external library. Real production would use `golang.org/x/sync/semaphore` or `errgroup` — same mechanism, the package handles the corners.

### Pipeline: generate → process (×2) → sum

![Diagram: gen feeds two square workers feeding the sum](/img/diagramas/go-conc-pipeline-en.svg)

```go title="main.go" showLineNumbers
func gen(nums ...int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for _, n := range nums {
			out <- n
		}
	}()
	return out
}

func square(in <-chan int) <-chan int {
	out := make(chan int)
	var wg sync.WaitGroup
	for i := 0; i < 2; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for n := range in {
				out <- n * n
			}
		}()
	}
	go func() {
		wg.Wait()
		close(out) // only closes after both finish
	}()
	return out
}

total := 0
for v := range square(gen(1, 2, 3, 4)) {
	total += v
}
fmt.Println("pipeline:", total)
```

```bash title="Terminal"
pipeline: 30
```

Each stage only knows channels (`<-chan` parameters document "I only read"). Close `out` once, by its owner, after `Wait` — closing twice or sending on closed: panic. It's the [Go Concurrency Patterns](https://go.dev/blog/pipelines) template applied by the book.

### The real `main`: timeouts, graceful shutdown, logger

Putting it together — request `context`, per-operation timeouts, a server with deadlines, shutdown without dropping connections:

```go title="main.go" showLineNumbers
mux.HandleFunc("/order", func(w http.ResponseWriter, r *http.Request) {
	// highlight-next-line
	ctx, cancel := context.WithTimeout(r.Context(), 1500*time.Millisecond)
	defer cancel()
	select {
	case <-time.After(200 * time.Millisecond):
		fmt.Fprintln(w, `{"status":"shipped"}`)
	case <-ctx.Done():
		http.Error(w, "timeout", http.StatusGatewayTimeout)
	}
})

srv := &http.Server{
	Addr:         "127.0.0.1:18099",
	Handler:      mux,
	ReadTimeout:  5 * time.Second,
	WriteTimeout: 5 * time.Second,
}

// highlight-next-line
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt)
defer stop()

go func() {
	if err := srv.ListenAndServe(); err != http.ErrServerClosed {
		log.Error("servidor", slog.Any("err", err))
	}
}()

<-ctx.Done() // waits for Ctrl+C / SIGTERM
shutCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
srv.Shutdown(shutCtx) // drains connections, then exits
```

```bash title="Terminal"
{"time":"...","level":"INFO","msg":"servindo","addr":"127.0.0.1:18099"}
{"status":"shipped"}
```

Up, answering, validated end to end. The decisions that matter: `r.Context()` as parent (client cancellation propagates alone), **per-operation** timeouts (not just server-wide), `Read/WriteTimeout` against Slowloris, `Shutdown` with a deadline instead of a hard kill. It's the skeleton from Jones Charles ([Context in practice](https://dev.to)) and Ajmani's Google Search example ([Go Concurrency Patterns: Context](https://go.dev/blog/context)) — no framework.

### Timeouts and cancellation: `select` + `context`

Two lines every backend writes: waiting with a deadline and obeying cancellation:

```go title="main.go" showLineNumbers
ch := make(chan string)
go func() {
	time.Sleep(2 * time.Second)
	ch <- "resultado"
}()

select {
case res := <-ch:
	fmt.Println("recebido:", res)
case <-time.After(100 * time.Millisecond):
	fmt.Println("timeout!")
}

ctx, cancel := context.WithTimeout(context.Background(), 50*time.Millisecond)
defer cancel()
select {
case <-ctx.Done():
	fmt.Println("cancelado:", ctx.Err())
case <-time.After(time.Second):
	fmt.Println("concluído")
}
```

```bash title="Terminal"
timeout!
cancelado: context deadline exceeded
```

`time.After` turns waiting into a `select` case; `ctx.Done()` closes when the deadline hits or the caller cancels — the worker takes whichever is ready first and drops the rest. That's how deadline-bearing requests cross handlers, queries, and calls without leaking goroutines.

### Cooperative cancellation: loops obeying `ctx`

One-shot timeouts solve one wait; long-lived workers must check cancellation every lap:

```go title="main.go" showLineNumbers
func worker(ctx context.Context, id int, done chan<- int) {
	for {
		select {
		case <-ctx.Done():
			done <- id
			return
		default:
			time.Sleep(100 * time.Millisecond) // works
		}
	}
}
```

```bash title="Terminal"
goroutines antes: 1
worker saiu: 2
worker saiu: 3
worker saiu: 1
goroutines depois: 1
```

`runtime.NumGoroutine()` before and after proves it: all 3 workers exited, nothing leaked. Goroutine counters + `pprof` are the leak-hunting kit: if the count only climbs between requests, some goroutine has no exit path — go back and give it a `ctx.Done()`.

## 5. Failures and trade-offs

**`Done` in the wrong place.** `wg.Add(1)` in the loop + `wg.Done()` in `main`'s consumption "works" while counts match — and becomes `negative WaitGroup counter` (panic) or eternal `Wait` at the first divergence. `defer wg.Done()` opens every worker goroutine, no exceptions.

**`time.Sleep` as synchronization.** Waiting "long enough" for goroutines is a timer guess: fails on slow machines, wastes on fast ones. Synchronize with `Wait`/`range`/channels — `Sleep` simulates latency in examples, never orders execution.

**Copying locks.** `sync.Mutex` inside value-passed structs: Post 2 showed `go vet` catching it. In concurrent code the damage is worse — two copies, two mutexes, zero real mutual exclusion.

**Deadlocks by ordering.** Two mutexes acquired in opposite order by different goroutines = deadly embrace. Rule: global acquisition order (always A→B), or better, one mutex plus channels.

**Leaked goroutines.** Sending on an unbuffered channel with no receiver forever = stuck goroutine + retained memory. Every `ch <- v` needs a `range`/receiver with a defined lifetime; every stage closes what it created.

**`-race` outside CI.** The detector costs ~10x CPU/memory — which is why it runs in tests, not production. `go test -race ./...` in the pipeline catches section 2's entire bug class before merge.
