Uma API HTTP em Go precisa de quatro coisas: ouvir numa porta, rotear path para função, ler/escrever JSON e logar com identidade. A stdlib entrega as quatro desde Go 1.22 — sem framework. Vamos construir nessa ordem, um arquivo inteiro por passo, terminando com o layout multi-arquivo que você usaria no trabalho e o mapa mental para quem vem do Spring.

Post avulso, validado com `curl` de verdade. Saídas reais, Go 1.26.

## 1. Contexto

Framework resolve o que a stdlib já resolve desde 1.22: rotear por método e padrão, servir com timeouts, encerrar com drenagem. Comece stdlib: menos camada para debugar, upgrade sem breaking. Framework entra quando doer de verdade (validação complexa, OpenAPI gerado) — não antes.

O que vamos construir, um passo por vez — cada passo é o arquivo inteiro, substitui o anterior e roda:

```text title="Layout final (passo 4)"
go-http-api/
  go.mod
  cmd/api/main.go              // Server + timeouts + shutdown
  internal/server/mux.go       // NewServeMux + rotas
  internal/handler/health.go   // GET /health
  internal/handler/double.go   // POST /double
  internal/middleware/requestid.go
  internal/middleware/logger.go
  internal/middleware/recover.go
```

![Diagrama: request atravessa middleware, handler, JSON de volta](/img/diagramas/go-http-cadeia.svg)

> **Resposta direta:** sim, `http.NewServeMux()` é a forma padrão na lib padrão. Desde Go 1.22 ele roteia por método (`"GET /health"`). Chi é um `ServeMux` com açúcar (grupos, params). Gin/Fiber/Echo são engines próprias — populares em vagas, mas fora da stdlib.

## 2. O problema

API sem request_id: três requests falham juntos e o log não diz qual é qual. Sem timeout: handler lento prende conexão para sempre. Sem Content-Type: cliente adivinha o corpo. Cada um desses já derrubou produção — e nenhum precisa de framework.

## 3. Modelo mental

Três definições antes do código. Leia esta seção uma vez — todo o resto do post é aplicação dela.

> **Definição (proposta): Handler.** Qualquer coisa com `ServeHTTP(w, r)`. Na prática, `func(w http.ResponseWriter, r *http.Request)`: `w` é por onde a resposta sai, `r` é o que chegou.

> **Definição (proposta): Mux.** Tabela de padrão → handler. `http.NewServeMux()` cria a tabela, `HandleFunc("GET /x", f)` registra uma linha. Na hora do request, ele casa método + path e chama o handler.

> **Definição (proposta): Middleware.** Função que recebe um handler e devolve outro: `func(next http.Handler) http.Handler`. Não é o destino — é a camada no meio. Intercepta antes (prepara), chama `next.ServeHTTP` (desce), intercepta depois (finaliza).

Middleware é cebola: a camada externa vê o request primeiro e a resposta por último. Ordem neste post, de fora para dentro: `recover` → `request_id` → `logger` → `mux`.

Middleware não é gateway. Middleware mora *dentro* de uma app (`server → middleware → handler`, a portaria do prédio). Gateway mora *na frente* de várias apps (`client → gateway → service A/B/C`, a entrada do condomínio). Gateway fica para um post futuro.

## 4. Implementação

Go 1.26, sem dependência. Passos 1–3: um `main.go` cada, rode com `go run .`. Passo 4: o módulo completo, rode com `go run ./cmd/api`.

### 4.1 Passo 1 — o menor servidor que responde

Arquivo inteiro:

```go title="main.go (passo 1)" showLineNumbers
package main

import "net/http"

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
		w.Write([]byte("ok"))
	})
	http.ListenAndServe("127.0.0.1:18098", mux)
}
```

Três peças, nada mais:

- **`http.NewServeMux()`** — o roteador: tabela de path → função.
- **`HandleFunc("GET /health", func...)`** — registra rota. O `"GET "` na frente (Go 1.22+) separa por método: mesmo path, métodos diferentes, funções diferentes.
- **A função handler** — sempre `func(w http.ResponseWriter, r *http.Request)`: `w` é por onde a resposta sai, `r` é o que chegou.

```bash title="Terminal"
$ go run .
$ curl http://127.0.0.1:18098/health
ok
```

Servidor no ar. Todo o resto deste post é camada sobre esse arquivo.

### 4.2 Passo 2 — JSON de verdade

Texto puro não é API. Trocamos a resposta por JSON e adicionamos uma rota POST que lê JSON. Arquivo inteiro — substitui o passo 1:

```go title="main.go (passo 2)" showLineNumbers
package main

import (
	"encoding/json"
	"net/http"
)

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		json.NewEncoder(w).Encode(map[string]string{"status": "ok"})
	})
	mux.HandleFunc("POST /double", func(w http.ResponseWriter, r *http.Request) {
		var in struct {
			N int `json:"n"`
		}
		if err := json.NewDecoder(r.Body).Decode(&in); err != nil {
			http.Error(w, "json inválido", http.StatusBadRequest)
			return
		}
		w.Header().Set("Content-Type", "application/json")
		json.NewEncoder(w).Encode(map[string]int{"result": in.N * 2})
	})
	http.ListenAndServe("127.0.0.1:18098", mux)
}
```

Duas regras que evitam bugs clássicos:

1. **Content-Type antes do primeiro `Encode`.** Depois que o primeiro byte sai, o header trava — cliente sem Content-Type adivinha o corpo (e proxy reescreve).
2. **JSON inválido = 400 honesto**, não 500. 400 diz "sua requisição está errada"; 500 diz "eu quebrei". Confundir os dois corrompe alerta e dashboard.

```bash title="Terminal"
$ go run .
$ curl http://127.0.0.1:18098/health
{"status":"ok"}
$ curl -X POST http://127.0.0.1:18098/double -d '{"n":21}'
{"result":42}
$ curl -X POST http://127.0.0.1:18098/double -d 'xxx'
json inválido
```

### 4.3 Passo 3 — middleware: quem é cada request

Com duas rotas, o log já mistura tudo. Separe em dois middlewares pequenos: um gera a identidade, o outro mede e loga. Arquivo inteiro — mesmos handlers do passo 2, agora embrulhados:

```go title="main.go (passo 3)" showLineNumbers
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"log/slog"
	"net/http"
	"os"
	"time"
)

type ctxKey string

const reqKey ctxKey = "request_id"

// RequestID gera a identidade na borda e pendura no contexto.
func RequestID(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		id := fmt.Sprintf("req-%d", time.Now().UnixNano()%100000)
		w.Header().Set("X-Request-ID", id)
		next.ServeHTTP(w, r.WithContext(context.WithValue(r.Context(), reqKey, id)))
	})
}

// FromContext lê o id sem parâmetro extra no handler.
func FromContext(ctx context.Context) string {
	if v, _ := ctx.Value(reqKey).(string); v != "" {
		return v
	}
	return "req-unknown"
}

// Logger mede a duração e loga com o request_id do contexto.
func Logger(log *slog.Logger, next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		next.ServeHTTP(w, r)
		log.Info("done",
			slog.String("request_id", FromContext(r.Context())),
			slog.String("method", r.Method),
			slog.String("path", r.URL.Path),
			slog.Duration("ms", time.Since(start)),
		)
	})
}

func main() {
	log := slog.New(slog.NewJSONHandler(os.Stdout, nil))

	mux := http.NewServeMux()
	mux.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		json.NewEncoder(w).Encode(map[string]string{"status": "ok"})
	})
	mux.HandleFunc("POST /double", func(w http.ResponseWriter, r *http.Request) {
		var in struct {
			N int `json:"n"`
		}
		if err := json.NewDecoder(r.Body).Decode(&in); err != nil {
			http.Error(w, "json inválido", http.StatusBadRequest)
			return
		}
		w.Header().Set("Content-Type", "application/json")
		json.NewEncoder(w).Encode(map[string]int{"result": in.N * 2})
	})

	h := RequestID(Logger(log, mux))
	http.ListenAndServe("127.0.0.1:18098", h)
}
```

Leia a montagem de dentro para fora: `mux` no centro, `Logger` embrulha o mux, `RequestID` embrulha tudo. `RequestID` por fora porque o `Logger` lê o id do contexto — se inverter, o logger loga `req-unknown`.

Leia um request de fora para dentro: gera `id`, carimba `ctx` e header, anota o relógio, **chama a próxima camada** (`next.ServeHTTP`), loga método + path + duração na volta.

```bash title="Terminal"
$ go run .
{"level":"INFO","msg":"done","request_id":"req-69000","method":"GET","path":"/health",...}
{"level":"INFO","msg":"done","request_id":"req-20000","method":"POST","path":"/double",...}
```

Três requests, três identidades — o log agora responde "qual falhou". Falta só o `recover` por fora de tudo e os timeouts: eles chegam no passo 4, junto com a divisão em arquivos.

### 4.4 Passo 4 — layout completo por arquivo

O passo 3 funciona, mas não cresce: tudo num `main.go` só. No trabalho, separe por responsabilidade — `cmd` monta, `internal` implementa. `RequestID` e `Logger` mudam de endereço sem mudar de corpo; o novo aqui é `Recover` + `http.Server` com timeouts e shutdown. Copie nessa estrutura e rode `go run ./cmd/api`.

```go title="go.mod"
module example.com/httpapi

go 1.26
```

**Regra prática.** Gere `request_id` na borda, nunca no handler. Tarde demais = middlewares anteriores já logaram sem ele.

```go title="internal/middleware/logger.go" showLineNumbers
package middleware

import (
	"log/slog"
	"net/http"
	"time"

// Logger mede duração e loga com o request_id do contexto.
func Logger(log *slog.Logger, next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		next.ServeHTTP(w, r)
		log.Info("done",
			slog.String("request_id", FromContext(r.Context())),
			slog.String("method", r.Method),
			slog.String("path", r.URL.Path),
			slog.Duration("ms", time.Since(start)),
		)
	})

```

```go title="internal/middleware/recover.go" showLineNumbers
package middleware

import (
	"log/slog"
	"net/http"
)

// Recover por fora de tudo: panic vira 500, servidor continua vivo.
func Recover(log *slog.Logger, next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		defer func() {
			if rec := recover(); rec != nil {
				log.Error("panic", slog.Any("panic", rec), slog.String("path", r.URL.Path))
				http.Error(w, "erro interno", http.StatusInternalServerError)
			}
		}()
		next.ServeHTTP(w, r)
	})
}
```


```go title="internal/server/mux.go" showLineNumbers
package server

import (
	"net/http"

	"example.com/httpapi/internal/handler"
)

// NewMux é a tabela de rotas: método + padrão → handler.
func NewMux() *http.ServeMux {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /health", handler.Health)
	mux.HandleFunc("POST /double", handler.Double)
	return mux
}
```

```go title="cmd/api/main.go" showLineNumbers
package main

import (
	"context"
	"errors"
	"log/slog"
	"net/http"
	"os"
	"os/signal"
	"time"

	"example.com/httpapi/internal/middleware"
	"example.com/httpapi/internal/server"
)

func main() {
	log := slog.New(slog.NewJSONHandler(os.Stdout, nil))

	mux := server.NewMux()
	// Cebola, de fora para dentro: recover → request_id → logger → mux.
	h := middleware.Recover(log, middleware.RequestID(middleware.Logger(log, mux)))

	srv := &http.Server{
		Addr:         "127.0.0.1:18098",
		Handler:      h,
		ReadTimeout:  5 * time.Second,
		WriteTimeout: 10 * time.Second,
		IdleTimeout:  60 * time.Second,
	}

	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt)
	defer stop()

	go func() {
		log.Info("listen", slog.String("addr", srv.Addr))
		if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
			log.Error("serve", slog.Any("err", err))
			os.Exit(1)
		}
	}()

	<-ctx.Done()
	shutCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	_ = srv.Shutdown(shutCtx)
}
```

```bash title="Terminal"
$ go run ./cmd/api
{"level":"INFO","msg":"listen","addr":"127.0.0.1:18098"}
$ curl http://127.0.0.1:18098/health
{"status":"ok"}
$ curl -X POST http://127.0.0.1:18098/double -d '{"n":21}'
```

Por que essa divisão: `handler` não conhece log nem middleware — só `w` e `r`. `server` só conhece rotas. `cmd/api` monta cebola e timeouts. Teste de handler vira chamada direta de função, sem subir servidor.

### Quem chama quem — o desenho da sequência

Duas sequências diferentes. A primeira acontece **uma vez** (montagem). A segunda acontece **a cada request**.

![Montagem no boot: main cria log, NewMux registra handlers, middlewares embrulham, http.Server escuta](/img/diagramas/go-http-montagem.svg)

Leia: `main` chama `server`, `server` aponta para `handler`, `main` embrulha tudo com `middleware`. Nenhum handler chama middleware — é o contrário.

![Cada request desce Recover, RequestID, Logger e Mux até o handler; a resposta sobe logando](/img/diagramas/go-http-request.svg)

**Regra prática.** Seta sempre desce na montagem e desce-volta no request. Se um handler importa middleware ou log, a seta inverteu — quebrou a camada.

## 5. Para quem vem do Spring (Java e Kotlin)

![Equivalência Spring para Go: Controller vira HandleFunc, Filter vira middleware, Jackson vira Encoder e Decoder](/img/diagramas/go-http-spring.svg)

Mesmo endpoint nas três formas — Java, Kotlin, Go. Note o que some: anotação, binding automático, serializador implícito.

```java title="DoubleController.java"
@PostMapping("/double")
public Map<String, Integer> doubleIt(@RequestBody Map<String, Integer> in) {
    return Map.of("result", in.get("n") * 2);
}
```

```kotlin title="DoubleController.kt"
@PostMapping("/double")
fun doubleIt(@RequestBody body: Map<String, Int>): Map<String, Int> {
    val n = body["n"] ?: throw ResponseStatusException(HttpStatus.BAD_REQUEST, "campo n ausente")
    return mapOf("result" to n * 2)
}
```

```go title="internal/handler/double.go"
func Double(w http.ResponseWriter, r *http.Request) {
	var in struct {
		N int `json:"n"`
	}
	if err := json.NewDecoder(r.Body).Decode(&in); err != nil {
		http.Error(w, "json inválido", http.StatusBadRequest)
		return
	}
	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(map[string]int{"result": in.N * 2})
}
```

O Kotlin deixa visível o que o Java esconde: o `400` precisa ser dito (`?: throw ... BAD_REQUEST`). Em Go ele também é dito — com `http.Error`. Nos três, a regra é a mesma; só muda onde ela mora: anotação/exceção vs chamada explícita.

Middleware também tem as três formas. Kotlin primeiro:

```kotlin title="RequestIdFilter.kt"
@Component
class RequestIdFilter : OncePerRequestFilter() {
    override fun doFilterInternal(
        request: HttpServletRequest,
        response: HttpServletResponse,
        chain: FilterChain,
    ) {
        val id = "req-${System.nanoTime() % 100000}"
        MDC.put("request_id", id)
        response.setHeader("X-Request-ID", id)
        try {
            chain.doFilter(request, response)
        } finally {
            MDC.clear()
        }
    }
}
```

```go title="internal/middleware/requestid.go (resumo)"
func RequestID(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		// ... gera id, carimba ctx + header ...
		next.ServeHTTP(w, r.WithContext(ctx)) // = chain.doFilter
	})
}
```

`chain.doFilter` é o `next.ServeHTTP`. `MDC` é o `context.Context` — com uma diferença que pega gente vindo do Spring: `MDC` é thread-local implícito, `ctx` é parâmetro explícito que viaja no `r`. Por isso a ordem da cebola importa mais em Go: se o `Logger` ficar por fora do `RequestID`, ele lê o contexto antes do carimbo e loga `req-unknown`.

### E MVC, faz sentido em Go?

![MVC em Go: Model é struct com tag, View é JSON na resposta, Controller é o handler; regra que cresce vira service mais repository](/img/diagramas/go-http-mvc.svg)

Onde o MVC estoura: quando a regra cresce, o handler vira controller gordo — Decode + regra + banco + Encode no mesmo lugar. No Spring você quebraria em `@Service` + `@Repository`; em Go, quebre igual: `handler` (HTTP: Decode 400 / Encode) → `service`/use case (regra pura, `n * 2`, testável sem servidor) → `repository` (interface; postgres/memória implementa, só se precisar persistir). É a porta de entrada da arquitetura hexagonal — sem framework, sem nome de pasta obrigatório, só direção de dependência para dentro, como no desenho acima.

Trade-off honesto: Spring entrega DI, validação (`@Valid` / `jakarta.validation`), OpenAPI gerado — cobra runtime maior, proxy/reflexão no stacktrace, lock-in de convenção. Stdlib entrega controle total e binário pequeno — cobra verbo: cada 400, cada header, cada timeout é código seu.

**Regra prática.** Vindo do Spring/Kotlin, resista a recriar anotação com framework no dia um — e resista a enfiar regra no handler. Fique na stdlib até sentir falta de validação complexa ou doc gerada — aí Chi/Gin pagam o custo; quando o handler engordar, extraia service antes de adotar framework.

## 6. Falhas e trade-offs

**Framework no dia um.** Chi/Gin/Fiber antes da primeira dor: camada para debugar, upgrade com breaking, lock-in de convenção. Adote quando a stdlib provar limite.

**Middleware único que faz tudo.** Um `mw` gigante (id + log + recover juntos) funciona no passo 3, mas não se testa nem se reordena. Separe um verbo por middleware — a divisão do passo 4 existe para isso.

**Sem timeout no servidor.** Handler com `ctx` não salva conexão sem `ReadTimeout`/`WriteTimeout` no `http.Server`: Slowloris ocupa workers de graça. Timeouts nas duas pontas + shutdown gracioso (a `main` real acima, mesmo padrão do post de [concorrência](/go-concorrencia)).

**`request_id` gerado no handler.** Tarde demais: middlewares anteriores já logaram sem ele. Gere na borda (primeiro middleware), propague via `ctx`.
