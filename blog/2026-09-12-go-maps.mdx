Até o Go 1.23, map era buckets com até 8 pares e correntes de overflow. O Go 1.24 trocou o runtime por Swiss Tables — grupos de 8 slots com control bytes comparados em conjunto, probing triangular, diretório e tabelas de no máximo 1024 slots ([Go Blog](https://go.dev/blog/swisstable)).

Este post é extra (fora da série Go por dentro): o mapa no nível da API você já usa; aqui vai o runtime atual, o que mudou e por quê — com a ressalva honesta de que detalhe de runtime muda entre versões.

## 1. Contexto

`m := make(map[string]int)` cria mais que "um dicionário": a variável guarda um **ponteiro** para a estrutura interna `Map` (campos `used`, `seed`, diretório...). Copiar a variável copia o ponteiro — dois nomes, um mapa. E `len(m)` é O(1) porque lê o contador `used`, não percorre nada.

Cada mapa nasce com um `seed` aleatório: o hash mistura chave + seed, então as mesmas chaves se distribuem diferente em mapas diferentes. Ordem de iteração? Consequência direta: **não confie nela** — varia entre execuções por construção.

## 2. O problema

Com buckets antigos, colisão virava corrente de overflow: cada elo, um load de ponteiro dependente antes de escanear 8 slots. Crescimento dobrava o array inteiro e evacuava incrementalmente, mantendo dois arrays vivos. Funcionava — mas pagava pointer chasing em toda colisão longa e rebuilds globais no crescimento. O Go 1.24 redesenhou para: comparar 8 candidatos de uma vez, procurar espaço no mesmo array contíguo e rebuildar só a tabela afetada.

## 3. Modelo mental

**Grupo: 8 slots + 8 control bytes.** A unidade mínima. Cada control byte descreve o slot abaixo: bit alto 0 = vivo (7 bits guardam H2, pedaço do hash); `10000000` = empty; `11111110` = deleted (tombstone):

![Diagrama: grupo com control bytes e slots](/img/diagramas/go-maps-group.svg)

**H1 escolhe onde começar; H2 filtra.** O hash se divide: H1 (57 bits) seleciona grupo de partida (e entrada do diretório, e tabela); H2 (7 bits) é comparado com os 8 control bytes **de uma vez** (SIMD no AMD64) gerando bitmask de candidatos. Só candidatos passam por comparação completa de chave (`==`). Chaves completas quase nunca são lidas à toa.

**Empty para, deleted continua.** Busca sem achar + control empty no grupo = pode parar (a chave não está adiante na sequência). Deleted = outra chave pode ter passado por ali antes de ser removida → continua sondando. Por isso deletar nem sempre marca tombstone: com slot empty no grupo (ou mapa de 1 grupo), o removido vira empty direto.

**Tabela, probing, diretório, load 7/8.** Grupos vivem em tabelas (até 128 grupos = 1024 slots); grupo cheio → próximo pela **sequência triangular de probing** (saltos crescentes evitam clustering do linear). Tabela cheia (carga 7/8 contando vivos + deletados) → dobra grupos ou, no limite, **split**: divide só aquela tabela em duas — as demais ficam intactas. O **diretório** mapeia prefixos de H1 para tabelas (profundidades global/local), permitindo splits independentes.

![Diagrama: buckets com overflow vs tabela com probing](/img/diagramas/go-maps-old-vs-new.svg)

**Regra prática.** Modelo de bolso: hash → H1 acha o grupo, H2 filtra 8 de uma vez, empty para, deleted segue, 7/8 manda crescer. Detalhe além disso, consulte o fonte da sua versão (`runtime/maps`).

## 4. Implementação

A API não mudou — o que muda é o que você pode assumir sobre ela:

```go title="main.go" showLineNumbers
m := make(map[string]int)
m["alice"] = 25
m["bob"] = 30
fmt.Println("len:", len(m))

v, ok := m["carol"]
fmt.Println("ausente:", v, ok)

delete(m, "alice")
fmt.Println("pos-delete:", len(m), m["alice"])
```

```bash title="Terminal"
len: 2
ausente: 0 false
pos-delete: 1 0
```

Três regras embutidas: `len` lê contador (O(1)); chave ausente devolve zero value — a forma `v, ok` distingue "vale zero" de "não existe" (mesma lição do nil tipado do Post 3); `delete` em chave inexistente é no-op seguro, e ler depois devolve o zero.

## 5. Falhas e trade-offs

**Iterar esperando ordem.** Seed aleatória + redistribuição = ordem varia. Precisa de ordem? Extraia chaves, ordene com `slices.Sorted(maps.Keys(m))`.

**Concorrência: map não é thread-safe.** Leitura concorrente com escrita = panic (`concurrent map read and map write`); escrita dupla = `fatal error`. Proteja com `sync.Mutex`/`RWMutex`, use `sync.Map` no padrão certo ou particione por goroutine.

**Ensinar buckets em 2026.** Tutoriais pré-1.24 (incluindo guias visuais antigos) descrevem overflow e evacuação incremental como "como Go faz". Hoje é história: cite como nota histórica, ensine Swiss Tables como atual — e marque a versão, porque runtime evolui (layout split-group já é experimento `GOEXPERIMENT=mapsplitgroup`, padrão no branch de dev).

**Premature tuning por internals.** Load 7/8, grupos de 8, probing — tudo é decisão de implementação, não contrato. Otimize por benchmark (como no Post 1), nunca por "li que o grupo tem 8 slots".
